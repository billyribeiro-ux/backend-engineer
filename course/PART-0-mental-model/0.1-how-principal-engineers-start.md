# Lesson 0.1 — How a Principal Engineer Starts a Project

## Before We Touch Anything

Most beginners open a code editor and start typing. They create a file called `index.js`, install some packages, and figure it out as they go.

A Principal Engineer does the opposite. They start by asking questions — and they don't write a single line of code until those questions are answered.

This isn't because they're slow. It's because they've seen what happens when you skip this step. You build something, ship it, and six months later you're rewriting half of it because the original design couldn't handle a requirement that was obvious from the beginning — if someone had just asked.

---

## The 3 Questions Asked Before Anything Else

Every system a Principal Engineer touches gets asked the same three questions:

### Question 1: What does this system DO?

Not "what features does it have." What does it actually do at its core?

This sounds obvious, but it forces precision. "It's an e-commerce site" is not an answer. "It sells two physical products and one subscription service, handles recurring billing, and lets admins change prices without breaking existing customers" — that's an answer. Now you know you need a billing system, a price versioning strategy, and an admin interface.

### Question 2: Who uses it?

These are called **actors** — anyone or anything that interacts with the system.

For our course project, the actors are:
- A **guest** — someone browsing before signing up
- A **member** — a registered user, possibly with an active subscription
- An **admin** — someone who manages the platform (changes prices, manages users, views reports)
- A **support agent** — someone who can view customer data to help with issues, but can't change prices or billing
- **Stripe** — yes, Stripe is an actor. It sends your system notifications (webhooks) when payments succeed or fail.

Once you list your actors, you immediately know you need a **role system**. Different actors can do different things.

### Question 3: What can go wrong?

This is where junior engineers stop thinking and senior engineers keep going.

What happens if:
- A user's payment fails — do they lose access immediately? After a grace period?
- You raise the price — do existing customers pay the new price?
- A webhook fires twice — do you charge the customer twice?
- Someone tries to brute-force the login endpoint?
- A support agent accidentally has access to billing controls?

You don't need answers yet. You need to *notice* the questions, because each one represents a decision you have to make — and if you don't make it consciously, the code will make it for you in the worst possible way.

---

## The Vocabulary (Explained in Plain English)

You'll hear these words constantly. Here's what they actually mean:

**System** — The software you're building. Not just the code — the database, the APIs, the background jobs, the integrations. All of it together.

**Actor** — Anyone or anything that interacts with your system. Users, admins, external services like Stripe, automated jobs.

**Entity** — A "thing" your system needs to track. A User is an entity. A Product is an entity. A Subscription is an entity. You'll store entities in database tables.

**Constraint** — A rule that must always be true. "A subscription must always belong to a user" is a constraint. "A price must always be greater than zero" is a constraint. Constraints prevent bad data from entering your system.

**Invariant** — A constraint that must hold at all times, even during complex operations. For example: "a user's subscription status and their access level must always agree — if one changes, the other must change atomically." The word "atomically" means: all at once, never halfway.

**Requirement** — Something the system must do. "Users can cancel their subscription" is a requirement. Requirements come from the business, not from the code.

**Behavior** — How the system responds to actions. "When a subscription is canceled, the user retains access until the end of the billing period" is a behavior.

---

## Why Beginners Skip This and Why That's Costly

Starting with code feels productive. You can see something happening. You're making progress.

The problem: code is the hardest thing to change. A wrong decision made in your database schema on day one will touch every query you write for the next two years. A wrong decision about how prices work will require rewriting your billing logic, your Stripe integration, and possibly migrating production data.

Words on paper cost nothing to change. A conversation costs nothing. A diagram costs 15 minutes.

Code costs weeks.

A Principal Engineer starts slow so they can move fast. By the time they write the first line of code, they already know:
- What the database looks like
- What every API endpoint does
- Who can call each endpoint
- What happens when things go wrong

That's not over-engineering. That's not being slow. That's the work that makes everything after it fast.
