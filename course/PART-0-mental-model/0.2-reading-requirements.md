# Lesson 0.2 — Reading the Business Requirements Like an Engineer

## What You're Actually Looking For

When a business person describes what they want, they speak in features and outcomes:

> "Users should be able to subscribe monthly or yearly, and we want to be able to offer discounts to certain customers without changing everyone's price."

When an engineer reads that same sentence, they're extracting four different things simultaneously:

1. **Actors** — who does things (users, admins)
2. **Entities** — what things exist (subscriptions, prices, discounts, customers)
3. **Behaviors** — what happens (subscribe, apply discount)
4. **Rules** — constraints that must hold (changing one price can't affect another customer)

Let's practice this on the actual project we're building.

---

## The Course Project Requirements

Here's the full description of what we're building:

> A SaaS platform with two products available for one-time purchase and one subscription tier available monthly, quarterly, or yearly. Admins can change product prices and subscription prices at any time. When a price changes, the admin can choose whether it applies to: (a) future members only, (b) all current and future members, or (c) members who joined after a specific date. Existing subscribers can be grandfathered into their original price. The platform supports coupon codes (percentage or fixed discount) and free trials. Multiple separate businesses can use the platform — each business has its own users, subscriptions, and data that must not mix with other businesses. Users have different roles: guest, member, admin, and support agent. The platform uses Stripe for all payments.

Now let's extract the four categories.

---

## Step 1: Extract the Actors

Go through the requirements and underline every person or system that does something or has something done to them.

| Actor | Description |
|-------|-------------|
| Guest | A visitor who hasn't registered. Can browse but can't buy. |
| Member | A registered user. Can purchase products and subscribe. |
| Admin | Can change prices, manage users, view reports. |
| Support Agent | Can view customer data to help with issues. Limited write access. |
| Stripe | An external system that processes payments and sends webhook notifications back to us. |

Notice what we haven't listed: "the system." The system isn't an actor — it's what we're building. But Stripe IS an actor because it has its own behavior and it talks back to us.

---

## Step 2: Extract the Entities

An entity is a "thing" the system needs to remember. If it needs to be stored in a database, it's an entity.

Go through the requirements again and circle every noun that represents something you'd need to keep track of:

| Entity | Why it exists |
|--------|--------------|
| User | The person using the platform. Separate from their auth credentials. |
| Organization | Each business using the platform (multi-tenant). |
| Role | What a user is allowed to do (member, admin, etc.). |
| Permission | A specific action a role can take. |
| Product | The two one-time purchasable items. |
| Price | The cost of a product or plan. Separate from the product itself. |
| Subscription Plan | Monthly / quarterly / yearly options. |
| Subscription | A user's active subscription to a plan. |
| Invoice | A billing record for a payment. |
| Payment | A record of money received. |
| Coupon | A discount code with rules (percent/fixed, expiry, max uses). |
| Coupon Redemption | A record of who used a coupon when. |
| Webhook Event | A record of every event received from Stripe. |
| Audit Log | A record of every significant action taken in the system. |

**Why is Price separate from Product?**

Because a product can have multiple prices over time. If a product costs $29 today and $39 next month, and some users are grandfathered, you can't just update a single `price` column on the product — you'd lose the history. The price history IS the data.

This is the same reason Stripe separates Products from Prices. They figured this out early.

**Why is Webhook Event an entity?**

Because Stripe sends the same event more than once. If you receive a `payment_intent.succeeded` event and process it (giving the user access), and then Stripe sends it again, you need to be able to check: "Did I already process event `evt_abc123`?" If you don't store events, you can't answer that question. If you can't answer it, you might process a payment twice.

---

## Step 3: Extract the Behaviors

A behavior is something that happens. It usually involves an actor doing something to an entity.

| Behavior | Actor | Trigger | What must happen |
|----------|-------|---------|-----------------|
| Register | Guest | Signs up | Create User, create Stripe Customer, assign default role |
| Login | Member/Admin | Provides credentials | Verify password, issue JWT token |
| Purchase product | Member | Clicks buy | Create PaymentIntent in Stripe, wait for webhook |
| Subscribe | Member | Chooses a plan | Create Stripe Subscription, store locally |
| Change price | Admin | Updates price form | Create new Price record with `applies_to` rule, don't delete old price |
| Apply coupon | Member | Enters code at checkout | Validate code, record redemption, adjust payment amount |
| Cancel subscription | Member | Clicks cancel | Tell Stripe, update local subscription status, set access end date |
| Receive webhook | Stripe | Payment/sub event | Verify signature, check if already processed, act on event |

Notice: "Purchase product" doesn't end when the user clicks buy. It ends when the webhook confirms payment. This is a critical mental shift — your system doesn't decide whether a payment succeeded. Stripe does. Your system listens and reacts.

---

## Step 4: Extract the Rules

Rules are constraints. Things that must ALWAYS be true, or things that must NEVER happen.

| Rule | Why it matters |
|------|---------------|
| A user's data must never be visible to another organization | Multi-tenant isolation — the most dangerous bug to get wrong |
| Price changes must not retroactively affect grandfathered users | Business promise to existing customers |
| A webhook must be verified before acting on it | Stripe signature verification — prevents fake webhook attacks |
| A webhook must be idempotent | Processing the same event twice must produce the same result as processing it once |
| Audit logs are append-only | You never update or delete audit logs — they're evidence |
| A coupon code can only be used the number of times specified | Max uses constraint |
| A coupon code cannot be used after its expiry date | Temporal constraint |
| A support agent cannot change prices or billing | Role constraint |
| Passwords must never be stored in plain text | Security invariant |

## What We Know Before Writing Code

After this exercise, we know:
- 5 actor types
- 14 entities (14 database tables, roughly)
- 8 core behaviors (each becomes one or more API endpoints)
- 9 rules (each becomes a constraint, middleware check, or database constraint)

This is the map. We haven't written a single line of code, and we already know more about this system than most developers know after building it.

## The Answer to the Exercise from Lesson 0.1

Here's what a Principal Engineer would have written:

**What does this system DO?**
It's a multi-tenant SaaS billing platform. It sells two one-time products and one subscription at three billing intervals. It manages price versioning with grandfathering, supports coupons and trials, and enforces role-based access across organizations. All money flows through Stripe; the platform listens to Stripe webhooks to confirm payment and update access.

**Who are the actors?**
Guest, Member, Admin, Support Agent, Stripe.

**What can go wrong?**
1. A webhook fires twice → user charged or granted access twice
2. A price change affects a grandfathered user → customer gets charged wrong amount
3. An admin accidentally sees another organization's data → multi-tenant breach
4. A coupon is used after it expires → revenue loss
5. A support agent is given too much access → unauthorized billing changes
6. A user's subscription lapses but they still have access → access control bug
7. A fake webhook arrives without signature verification → unauthorized data manipulation
8. A trial ends but the user isn't notified → churn and confusion

Every item on that list is a decision you have to make in code. The earlier you see them, the easier they are to handle.
