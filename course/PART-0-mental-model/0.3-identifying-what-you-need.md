# Lesson 0.3 — Identifying What You Need Before You Need It

## The If-Then Checklist

A Principal Engineer doesn't randomly decide what infrastructure to build. They run a mental checklist — a series of "if this is true about the system, then you need this" patterns.

These patterns come from having built enough systems to recognize that certain requirements always lead to the same infrastructure decisions. Once you internalize them, you'll never start a project without knowing what you need.

Let's run every question against our course project.

---

## The Checklist

### Does it have users?
**→ You need authentication.**

Authentication (auth) is the system that proves who someone is. It requires:
- A way to register (create an account)
- A way to log in (verify identity)
- A way to stay logged in (sessions or tokens)
- Password hashing (never store plain passwords)

**For our project:** Yes, users register and log in. We need auth.

---

### Do different users see or do different things?
**→ You need roles. That means RBAC (Role-Based Access Control).**

RBAC is the system that controls what a user is allowed to do based on their "role" — their job title, essentially. An admin can do things a member can't.

In plain English: your job title determines what you can do.

RBAC requires:
- A `roles` table (admin, member, guest, support)
- A `permissions` table (specific actions each role can take)
- A way to assign roles to users
- Middleware that checks roles before allowing access

**For our project:** Yes. Admins change prices. Support agents view data. Members buy things. Guests can only browse. We need RBAC.

---

### Does access depend on context — ownership, state, or time?
**→ You need ABAC (Attribute-Based Access Control).**

ABAC is the system that controls access based on the situation. Not just "what is your role" but "what is your role, what are you trying to touch, do you own it, and is your account in a valid state?"

In plain English: it depends on the situation.

ABAC requires:
- Policy functions that evaluate attributes at request time
- Attributes on the subject (the user: their role, plan status, org membership)
- Attributes on the resource (the thing being accessed: its owner, its state)
- Attributes on the environment (the context: subscription active? trial expired?)

**For our project:** Yes.
- A member can only edit their OWN profile, not another member's
- A member can only access premium features while their subscription is `active` or `trialing`
- A support agent can view a customer's subscription but cannot modify it
- We need ABAC on top of RBAC.

---

### When do you use RBAC, ABAC, or both?

This is the question that trips up even experienced engineers. Here's the rule:

**Use RBAC when** access is based on the user's role alone, regardless of context:
- "Only admins can access the admin dashboard" — no context needed
- "Only admins can change prices" — doesn't matter which price or whose account
- "Only members can purchase" — role-only check

**Use ABAC when** access depends on the specific situation:
- "A user can edit their own post" — depends on ownership (resource attribute)
- "A user can access premium content" — depends on subscription status (subject attribute)
- "A user can view their invoice" — depends on whether the invoice belongs to them

**Use both when** you need a role gate AND contextual rules:
- "Only admins can delete users, and only if the user account is not the organization owner" — first check role (admin), then check attribute (is target the org owner?)
- "Only support agents can view subscriptions, and only for their assigned customers" — first check role (support), then check attribute (is this customer assigned to this agent?)

**Real-world example — hospitals:**
Hospitals use RBAC + ABAC together constantly.

RBAC alone says: "Doctors can view patient records, nurses can view patient records, billing staff can view invoices."

But RBAC alone isn't enough. A cardiologist shouldn't see psychiatric records. A surgeon in one wing shouldn't see ICU records from another. So ABAC adds: "You can view patient records IF the patient is assigned to your department AND you have an active shift AND you have been granted access to this specific record type."

The role (doctor) grants the broad permission. The attributes (department, shift, record type, patient assignment) narrow it to exactly what's appropriate.

**Our project's breakdown:**

| Action | RBAC check | ABAC check |
|--------|-----------|-----------|
| View admin dashboard | Is role `admin`? | — |
| Change a price | Is role `admin`? | — |
| Edit own profile | Is role `member` or `admin`? | Is `user.id === resource.owner_id`? |
| Access premium content | Is role `member`? | Is `user.subscription.status === 'active'`? |
| View a subscription | Is role `support` or `admin`? | For `support`: is customer assigned to this agent? |
| Delete a user | Is role `admin`? | Is target user NOT the org owner? |

### Does money change hands?
**→ You need idempotency, audit logs, and webhook handling.**

**Idempotency** (pronounced "eye-dem-PO-ten-see") means: doing the same thing twice produces the same result as doing it once. In billing systems, this means: if a webhook fires twice, you process the payment once, not twice.

**Audit logs** are an immutable (unchangeable) record of everything that happened. In billing, you need to know exactly what happened and when — for disputes, refunds, support tickets, and legal compliance.

**Webhooks** are how payment providers (like Stripe) notify your system. You don't poll Stripe asking "did the payment succeed?" — Stripe tells you. Your job is to receive that notification, verify it's real, check if you already handled it, and then act on it.

**For our project:** Yes, money changes hands. We need all three.

---

### Will prices change over time?
**→ You need price versioning and grandfathering logic.**

Price versioning means storing the history of prices, not just the current price. If you overwrite the price column, you lose the history. If you lose the history, you can't honor grandfathered rates.

**For our project:** Yes. Admins can change prices. Grandfathering is a core requirement.

---

### Will multiple separate businesses use this?
**→ You need multi-tenancy.**

Multi-tenancy means one copy of the software serves multiple separate organizations, and each organization's data is completely isolated from every other.

The most dangerous bug in multi-tenant systems: forgetting to filter by organization. A user from Company A accidentally sees Company B's invoices. This is a data breach.

**For our project:** Yes. We'll build single-tenant first, then add multi-tenancy in Part 7.

---

### Will you have background jobs or scheduled tasks?
**→ You need a job queue or scheduler.**

Background jobs are tasks that run outside the normal request-response cycle. For example: "send a trial expiry email 3 days before the trial ends." You can't do this in a request handler — you need something that runs on a schedule.

**For our project:** We need a job to check for trials expiring soon and send notifications. We'll cover the trigger mechanism without building a full job system (that's a course on its own).

## The Full Shopping List

After running every question, here's what our system needs:

| Infrastructure | Why |
|---------------|-----|
| Authentication (JWT) | Users log in |
| RBAC | Different roles, different access |
| ABAC | Ownership and subscription-state checks |
| Database (PostgreSQL) | Persistent storage for all entities |
| ORM / Query Builder | Typed, safe database access |
| Price versioning | Prices change, grandfathering needed |
| Stripe integration | All payments go through Stripe |
| Webhook handler | Stripe tells us when things happen |
| Idempotency layer | Webhooks fire more than once |
| Coupon engine | Discount codes with rules |
| Trial logic | Free trial periods |
| Audit logging | Immutable record of all significant actions |
| Multi-tenancy | Multiple organizations, isolated data |
| Rate limiting | Protect login and sensitive endpoints |
| Error handling | Safe, consistent error responses |
| Database migrations | Schema changes over time |
| Seed scripts | Pre-load roles, permissions, and test data |
| Environment variables | Config and secrets, never hardcoded |

This is the map. Every item on this list becomes a set of lessons in this course.

---

## The Key Insight

Notice what we haven't done: we haven't chosen a framework. We haven't installed anything. We haven't written any code.

And yet we know more about what this system needs than most teams figure out after a month of building.

The infrastructure list above is language-agnostic. It doesn't matter if you use Node.js, Python, Go, or Rust — you need every item on this list. That's why Part 9 of this course rebuilds everything in Rust without feeling like starting over. The mental model transfers.
