# Lesson 0.4 — Naming Things (The Hardest Problem in Engineering)

## Why Names Matter More Than You Think

There's a famous saying in computer science: "There are only two hard things: cache invalidation and naming things."

Cache invalidation is a technical problem. Naming is a human problem — and human problems are always harder.

Bad names cause bugs. They cause bugs because they create ambiguity in your head. When you write `user.id` but you mean "the ID of the person logged in," and somewhere else you write `user.id` and you mean "the ID of the customer record in Stripe," you will eventually use the wrong one in the wrong place. And it won't be obvious. It'll look correct.

Good names make wrong code look wrong. That's the goal.

---

## The `user_id` Problem

Let's start with the most common naming confusion in backend systems.

In most apps, a "user" actually means at least three separate things:

1. **The auth identity** — the record that proves someone can log in. It has an email and a hashed password. It might be managed by a third-party service. This is "who you are."

2. **The business profile** — the record that represents the person as a customer. Their name, their preferences, their subscription status. This is "what we know about you."

3. **The Stripe customer** — Stripe's record of the customer, used for billing. This lives in Stripe's database, not yours, but you reference it with a `stripe_customer_id`.

If you name all three "user" and put them all in one table, you'll constantly wonder: "When I say `user.id`, do I mean my database ID? The Stripe customer ID? Is this the auth record or the profile?"

**The correct approach:**

| Table name | What it stores | ID column |
|-----------|---------------|-----------|
| `users` | Auth identity — email, hashed password | `id` (UUID) |
| `profiles` or `accounts` | Business profile — name, preferences | `id` (UUID), `user_id` FK |
| *(Stripe-side)* | Stripe customer | `stripe_customer_id` stored in `users` or `profiles` |

Now when you write `user.stripe_customer_id`, it's unambiguous: it's the Stripe reference stored on the user record. When you write `profile.display_name`, it's unambiguous: it's the business-facing profile.

For our course project, we'll keep it slightly simpler and store both auth and profile data in a `users` table, with `stripe_customer_id` as a column. But we'll be precise about what each column means.

## The Golden Rules of Naming

### Rule 1: Name tables as plural nouns
`users` not `user`. `subscriptions` not `subscription`. `webhook_events` not `webhook_event`.

Why: a table is a collection of things. Collections are plural.

### Rule 2: Name foreign keys as `{referenced_table_singular}_{id}`
`user_id` points to the `users` table. `organization_id` points to the `organizations` table. `plan_id` points to the `plans` table.

Never: `userId`, `user`, `theUserId`, `uid`. Always: `user_id`.

### Rule 3: Use `snake_case` for database column names
`created_at` not `createdAt`. `stripe_customer_id` not `stripeCustomerId`.

SQL was designed with `snake_case` in mind. Many databases are case-insensitive by default. `snake_case` is unambiguous.

In your Node.js or Rust code you'll convert to `camelCase` where appropriate — but the database always speaks `snake_case`.

### Rule 4: Timestamp columns are always the same four names

Every table has:
- `id` — the primary key (UUID)
- `created_at` — when the row was created
- `updated_at` — when the row was last changed
- `deleted_at` — when the row was soft-deleted (NULL means not deleted)

These four columns appear on every table. No exceptions. Why? Because you will always need to know when something was created, changed, or deleted. If you don't add `deleted_at`, you'll add it later under pressure and regret not having it from the start.

### Rule 5: Status columns use clear, specific strings

Don't use numbers for status. Don't use cryptic abbreviations.

Bad: `status = 1` (what does 1 mean? Check the docs... if there are any)
Bad: `status = 'a'` (active? archived? approved?)
Good: `status = 'active'` | `'trialing'` | `'past_due'` | `'canceled'` | `'unpaid'`

Use the exact strings that Stripe uses for subscription statuses. That way, when Stripe sends you a status in a webhook, you can store it directly without translation.

### Rule 6: Boolean columns start with `is_` or `has_`

`is_active`, `has_trial`, `is_verified`, `has_agreed_to_terms`.

This makes the column's nature unmistakable. `active` is ambiguous (is it a status string or a boolean?). `is_active` is always a boolean.

### Rule 7: Amount/money columns are always integers in cents

Never store money as a floating-point decimal. `0.1 + 0.2` in most programming languages does not equal `0.3` exactly — floating-point math has precision issues.

Store `$29.99` as `2999` (cents). Stripe does this too. When displaying to users, divide by 100.

This is why you'll see `amount_cents` as a column name — it makes it clear the value is in cents.

### Rule 8: Don't abbreviate unless the abbreviation is universal

`org_id` is fine — "org" is universally understood to mean organization.
`usr_id` is not fine — just write `user_id`.
`sub_id` is ambiguous — `subscription_id` is clear.
`stripe_cust_id` is not fine — `stripe_customer_id` takes 3 more characters and is unambiguous.

Characters are free. Confusion is expensive.

## The Auth Identity vs Business Identity Split

This deserves its own section because it's one of the most common design mistakes.

**Auth identity answers:** Can this person log in?
**Business identity answers:** Who is this person to our system?

They start the same but diverge over time. Here's why they need to be separate concepts even if they live in one table:

Imagine you add Single Sign-On (SSO) later — users log in with Google instead of a password. Your auth mechanism changes completely, but the user's subscription, purchase history, and profile should not change at all.

If auth and business data are tangled together, adding SSO becomes a migration nightmare. If they're conceptually separate (even if physically in one table), you just change how the auth column works.

For our course project, we'll use one `users` table but keep the columns clearly separated in our mental model:

**Auth columns on `users`:**
- `id`
- `email`
- `password_hash`
- `email_verified_at`
- `last_login_at`
- `created_at`, `updated_at`, `deleted_at`

**Business/profile columns on `users`:**
- `display_name`
- `stripe_customer_id`
- `organization_id`

**Access control columns on `users`:**

## Naming the Course Project's Tables

Here's the final table list with names decided:

| Table | What it stores |
|-------|---------------|
| `users` | Auth identity + basic profile |
| `organizations` | Each business using the platform (multi-tenant) |
| `organization_members` | Which users belong to which organization with what role |
| `roles` | Role definitions (admin, member, guest, support) |
| `permissions` | Permission definitions (products:write, subscriptions:manage, etc.) |
| `role_permissions` | Which permissions belong to which role |
| `products` | The two purchasable items |
| `prices` | Historical prices for products and plans |
| `plans` | Subscription plan definitions (monthly, quarterly, yearly) |
| `subscriptions` | A user's active subscription |
| `invoices` | Billing records |
| `payments` | Payment records (tied to invoices) |
| `coupons` | Discount code definitions |
| `coupon_redemptions` | Record of who used which coupon |
| `webhook_events` | Every event received from Stripe |
| `audit_logs` | Immutable record of all significant actions |

16 tables. Each one has a clear, unambiguous name. Each one stores exactly one kind of thing.

## The Permission Naming Convention

Permissions follow a `resource:action` pattern:

```
products:read
products:write
products:delete
subscriptions:read
subscriptions:manage
subscriptions:cancel
users:read
users:manage
prices:read
prices:write
coupons:read
coupons:write
reports:read
```

This format makes it immediately clear what a permission allows: "the `products:write` permission lets you create and update products." No documentation needed.
