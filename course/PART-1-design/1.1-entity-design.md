# Lesson 1.1 — Entity Relationship Design

## Turning Words Into a Diagram

In the last two lessons we identified 16 entities. Now we need to understand how they relate to each other. This is called an **Entity Relationship Diagram** (ERD) — it's a drawing of all the things in your system and the connections between them.

You don't need special software for this. A whiteboard, a napkin, or a text file works fine. The goal is to think through the relationships before writing SQL, because once you write SQL and run migrations, changes are expensive.

---

## Types of Relationships

There are three types of relationships between entities:

**One-to-One (1:1)**
One record in Table A belongs to exactly one record in Table B, and vice versa.
Example: A `user` has one `stripe_customer_id`. One Stripe customer belongs to one user.

**One-to-Many (1:N)**
One record in Table A can relate to many records in Table B.
Example: One `organization` has many `users`. One `product` has many `prices` (over time).

**Many-to-Many (M:N)**
Many records in Table A can relate to many records in Table B.
Example: A `user` can have many `roles`, and a `role` can belong to many `users`.

Many-to-many relationships always require a **junction table** — a third table that sits between the two and stores the connection.

## Walking Through the Critical Relationships

### Organizations → Users (Many-to-Many via `organization_members`)

A user might belong to more than one organization (imagine a consultant who manages multiple clients' accounts). An organization definitely has many users.

The `organization_members` table is the junction:
```
organization_members
  - id
  - organization_id  (FK → organizations)
  - user_id          (FK → users)
  - role_id          (FK → roles)   ← role WITHIN this org
  - created_at
```

This table also stores the user's **role within that organization**. Being an admin of Org A doesn't make you an admin of Org B. The role lives on the membership, not on the user.

### Products → Prices (One-to-Many)

This is the most important relationship to understand for the grandfathering requirement.

A product doesn't have "a price." A product has a **price history**. The current price is the most recent one. Old prices are kept forever because some users are paying them.

```
products
  - id
  - name
  - description
  - is_active

prices
  - id
  - product_id        (FK → products, nullable if this is a plan price)
  - plan_id           (FK → plans, nullable if this is a product price)
  - amount_cents      (e.g., 2999 = $29.99)
  - currency          (e.g., 'usd')
  - applies_to        ('future_members' | 'all_members' | 'from_date')
  - applies_from_date (date, only used when applies_to = 'from_date')
  - stripe_price_id   (Stripe's ID for this price)
  - created_at
```

When an admin changes a price, they don't UPDATE the existing price row. They INSERT a new price row with the new amount and the rule for who it applies to. The old row stays. Now you can always answer: "What price was this subscription created at?" and "What price should this user be charged now?"

### Subscriptions → Prices (Grandfathering)

```
subscriptions
  - id
  - user_id
  - organization_id
  - plan_id
  - locked_price_id    (FK → prices — the price locked in at subscription time)
  - stripe_subscription_id
  - status             ('active' | 'trialing' | 'past_due' | 'canceled' | 'unpaid')
  - trial_ends_at
  - current_period_start
  - current_period_end
  - canceled_at
  - created_at
  - updated_at
  - deleted_at
```

The `locked_price_id` is the grandfathering mechanism. When a user subscribes, you record which price they agreed to. If the price changes later, their `locked_price_id` still points to the old price. When Stripe charges them, it uses their Stripe subscription's price (which you also manage). The two stay in sync.

### Webhook Events (Standalone)

```
webhook_events
  - id
  - stripe_event_id    (the unique ID Stripe sends, e.g., 'evt_abc123')
  - event_type         (e.g., 'invoice.paid')
  - payload            (JSON — the full event data from Stripe)
  - processed_at       (NULL if not yet processed)
  - created_at
```

When a webhook arrives:
1. Check if `stripe_event_id` already exists in this table → if yes, skip (already processed)
2. If no, insert the event record
3. Process the event
4. Update `processed_at` to now

This guarantees idempotency. The `stripe_event_id` column has a UNIQUE constraint — you literally cannot insert the same event twice.

### Audit Logs (Append-Only)

```
audit_logs
  - id
  - actor_id           (user_id of who did it, nullable for system actions)
  - actor_type         ('user' | 'system' | 'stripe')
  - action             (e.g., 'subscription.canceled', 'price.updated')
  - resource_type      (e.g., 'subscription', 'price', 'user')
  - resource_id        (UUID of the affected record)
  - metadata           (JSON — any additional context)
  - ip_address         (for security audit trails)
  - created_at         ← NO updated_at, NO deleted_at. This is intentional.
```

Audit logs have no `updated_at` and no `deleted_at`. They are written once and never changed. If you need to correct an audit log, you write a NEW log entry explaining the correction. The original stays.

## The Three Patterns to Memorize

After drawing enough ERDs, three patterns appear over and over:

**Pattern 1: The History Table**
When values change over time and history matters, make a separate table for history. (`prices` is an example.)

**Pattern 2: The Junction Table with Payload**
When a many-to-many relationship has attributes of its own, the junction table carries those. (`organization_members` carries the user's role in that org.)

**Pattern 3: The Standalone Log**
Some tables don't belong to any other entity — they're records of events. They reference other entities but aren't owned by them. (`webhook_events` and `audit_logs` are examples.)
