# Lesson 1.4 — The `.env.example` File (When and Why)

## What Are Environment Variables?

Your application needs certain values to run: a database connection string, an API key for Stripe, a secret for signing JWTs. These values are different depending on where the app runs:
- Your laptop (development) has a local database
- A staging server has a different database
- Production has the real database and the real Stripe keys

**Environment variables** are the solution. Instead of hardcoding `postgres://localhost:5432/mydb` in your code, you read it from the environment: `process.env.DATABASE_URL`. The code stays the same; the value changes per environment.

---

## The Two Files

**`.env`** — Your actual secrets. This file is on your machine only. It is NEVER committed to git. Every developer has their own. Production has its own. If this file leaks, it's a security incident.

**`.env.example`** — A template showing what variables the app needs, with placeholder values (not real secrets). This IS committed to git. It's documentation. When a new developer joins, they copy `.env.example` to `.env` and fill in the real values.

---

## When Do You Create `.env.example`?

**At project initialization. Before writing any code that needs configuration.**

The discipline: every time you need a new secret or config value, add it to `.env.example` IMMEDIATELY — with a comment explaining what it is and where to get it.

If you add a Stripe secret key to your code without adding it to `.env.example`, the next developer (or future you on a new machine) will have an app that silently fails because the variable is missing.

---

## What Belongs in `.env.example`

**Yes:**
- Database connection strings
- API keys for external services (Stripe, SendGrid, etc.)
- JWT secrets
- App port and base URL
- Feature flags
- Service URLs (Redis, queue servers)

**No:**
- Actual secrets (`.env.example` is committed to git)
- Computed values (derive these in code, don't make them configurable)
- Passwords that belong in a secrets manager in production

## The Course Project's `.env.example`

This is the complete file. Every variable is annotated. This file lives at the root of the project.

```bash
# =============================================================
# APPLICATION
# =============================================================

# The port your server listens on
PORT=3000

# The public URL of your app (used for email links, redirects)
# No trailing slash
APP_URL=http://localhost:3000

# The environment: development, staging, production
NODE_ENV=development

# =============================================================
# DATABASE
# =============================================================

# Full PostgreSQL connection string
# Format: postgres://USER:PASSWORD@HOST:PORT/DATABASE
DATABASE_URL=postgres://postgres:password@localhost:5432/saas_dev

# For running tests — uses a separate database so tests don't corrupt dev data
DATABASE_TEST_URL=postgres://postgres:password@localhost:5432/saas_test

# Connection pool settings (how many simultaneous DB connections)
DATABASE_POOL_MIN=2
DATABASE_POOL_MAX=10

# =============================================================
# AUTHENTICATION
# =============================================================

# Secret used to sign JWT access tokens
# Generate with: openssl rand -base64 64
# NEVER share this. If compromised, rotate immediately and invalidate all sessions.
JWT_ACCESS_SECRET=your-access-secret-here

# Secret used to sign JWT refresh tokens (should be different from access secret)
# Generate with: openssl rand -base64 64
JWT_REFRESH_SECRET=your-refresh-secret-here

# How long access tokens are valid
# Format: number + unit (s=seconds, m=minutes, h=hours, d=days)
JWT_ACCESS_EXPIRES_IN=15m

# How long refresh tokens are valid
JWT_REFRESH_EXPIRES_IN=30d

# Number of bcrypt hashing rounds (higher = slower but more secure)
# 12 is a good balance for production. 8 for tests (faster).
BCRYPT_ROUNDS=12

# =============================================================
# STRIPE
# =============================================================

# Stripe secret key — found in Stripe Dashboard → Developers → API Keys
# Test mode keys start with sk_test_
# Production keys start with sk_live_
# NEVER commit the real key. NEVER use live keys in development.
STRIPE_SECRET_KEY=sk_test_your_key_here

# Stripe publishable key — safe to expose to the frontend (it's public)
STRIPE_PUBLISHABLE_KEY=pk_test_your_key_here

# Stripe webhook signing secret
# Found in Stripe Dashboard → Developers → Webhooks → your endpoint → Signing secret
# Used to verify that webhook events actually came from Stripe (not a fake request)
# For local development, use the Stripe CLI: stripe listen --print-secret
STRIPE_WEBHOOK_SECRET=whsec_your_secret_here

# =============================================================
# EMAIL (using SendGrid — swap for your provider)
# =============================================================

# SendGrid API key for sending transactional emails
# Get from sendgrid.com → Settings → API Keys
SENDGRID_API_KEY=SG.your_key_here

# The email address that appears in the "From" field
# Must be a verified sender in SendGrid
EMAIL_FROM=noreply@yourapp.com

# =============================================================
# REDIS (for rate limiting and session storage)
# =============================================================

# Redis connection URL
# Format: redis://[:password@]host[:port][/db-number]
REDIS_URL=redis://localhost:6379

# =============================================================
# CORS
# =============================================================

# Allowed origins for CORS (comma-separated)
# In development this is typically your frontend dev server
# In production this is your actual frontend domain
CORS_ORIGINS=http://localhost:5173,http://localhost:3001

# =============================================================
# RATE LIMITING
# =============================================================

# Max login attempts per window
RATE_LIMIT_LOGIN_MAX=5
# Window in minutes for login rate limiting
RATE_LIMIT_LOGIN_WINDOW_MINUTES=15

# General API rate limit per authenticated user
RATE_LIMIT_API_MAX=100
# Window in minutes for general API rate limiting
RATE_LIMIT_API_WINDOW_MINUTES=1

# =============================================================
# LOGGING
# =============================================================

# Log level: error, warn, info, debug
LOG_LEVEL=info

# =============================================================
# FEATURE FLAGS (optional — for staged rollouts)
# =============================================================

# Enable trial periods (set to false to disable trials globally)
FEATURE_TRIALS_ENABLED=true

# Default trial length in days
TRIAL_DAYS=14
```

## The `.gitignore` Entry

Your `.gitignore` (the file that tells git what NOT to track) must contain:

```
# Environment files — NEVER commit these
.env
.env.local
.env.production
.env.staging

# But DO commit the example
# (no entry for .env.example)
```

---

## The Workflow a Principal Engineer Uses

1. **New project**: Create `.env.example` with every known variable before writing any code
2. **New developer onboards**: `cp .env.example .env` → fill in real values
3. **Adding a new integration**: Add the new variable to `.env.example` BEFORE writing the code that uses it
4. **Pre-commit hook**: Consider a linter that checks your codebase for hardcoded secrets

## Loading Environment Variables in Code

**Node.js** — use the `dotenv` package:
```javascript
// This goes at the very top of your entry file
import 'dotenv/config'

// Now process.env.DATABASE_URL etc. are available everywhere
```

**Rust** — use the `dotenvy` crate:
```rust
// In main.rs, before anything else
dotenvy::dotenv().ok();

let database_url = std::env::var("DATABASE_URL")
    .expect("DATABASE_URL must be set");
```

## The Config Module Pattern

Don't scatter `process.env.SOMETHING` throughout your codebase. Instead, create a `config.js` (or `config.ts`) module that reads all environment variables once at startup, validates them, and exports a typed config object:

```javascript
// config.js
const requiredEnvVars = [
  'DATABASE_URL',
  'JWT_ACCESS_SECRET',
  'JWT_REFRESH_SECRET',
  'STRIPE_SECRET_KEY',
  'STRIPE_WEBHOOK_SECRET',
]

for (const envVar of requiredEnvVars) {
  if (!process.env[envVar]) {
    throw new Error(`Missing required environment variable: ${envVar}`)
  }
}

export const config = {
  port: parseInt(process.env.PORT ?? '3000'),
  appUrl: process.env.APP_URL,
  nodeEnv: process.env.NODE_ENV ?? 'development',
  
  db: {
    url: process.env.DATABASE_URL,
    testUrl: process.env.DATABASE_TEST_URL,
    poolMin: parseInt(process.env.DATABASE_POOL_MIN ?? '2'),
    poolMax: parseInt(process.env.DATABASE_POOL_MAX ?? '10'),
  },
  
  auth: {
    accessSecret: process.env.JWT_ACCESS_SECRET,
    refreshSecret: process.env.JWT_REFRESH_SECRET,
    accessExpiresIn: process.env.JWT_ACCESS_EXPIRES_IN ?? '15m',
    refreshExpiresIn: process.env.JWT_REFRESH_EXPIRES_IN ?? '30d',
    bcryptRounds: parseInt(process.env.BCRYPT_ROUNDS ?? '12'),
  },
  
  stripe: {
    secretKey: process.env.STRIPE_SECRET_KEY,
    publishableKey: process.env.STRIPE_PUBLISHABLE_KEY,
    webhookSecret: process.env.STRIPE_WEBHOOK_SECRET,
  },
  
  email: {
    sendgridApiKey: process.env.SENDGRID_API_KEY,
    from: process.env.EMAIL_FROM,
  },
  
  redis: {
    url: process.env.REDIS_URL ?? 'redis://localhost:6379',
  },
  
  features: {
    trialsEnabled: process.env.FEATURE_TRIALS_ENABLED === 'true',
    trialDays: parseInt(process.env.TRIAL_DAYS ?? '14'),
  },
}
```

Now everywhere in your app you import `config` and use `config.stripe.secretKey` — never `process.env.STRIPE_SECRET_KEY`. If you ever rename a variable, you change it in one place. If validation fails at startup, the app refuses to start rather than failing mysteriously at runtime.

---

## Summary

| Practice | Why |
|----------|-----|
| Create `.env.example` at project init | Documents all required config before code needs it |
| Never commit `.env` | Prevents secret leaks |
| Validate all required vars at startup | Fail fast rather than fail mysteriously |
| Use a `config` module | Single place to read and type all env vars |
| Add to `.env.example` when adding new integrations | Keeps documentation current |
