# Lesson 2.1 — Authentication vs Authorization

## The Most Confused Pair in Backend Engineering

These two words are often used interchangeably by beginners. They're not the same thing. Confusing them leads to security bugs.

**Authentication (AuthN):** Proving who you are.
> "I am Alice. Here is my password. Now you know it's me."

**Authorization (AuthZ):** Proving you're allowed to do what you're trying to do.
> "Alice, you're logged in. But are you allowed to delete this product? Let me check your role... No, only admins can do that."

Authentication comes first. You can't authorize someone whose identity you don't know.

---

## A Concrete Analogy

Think of a hotel.

**Authentication** is checking in at the front desk. You show your ID, they verify it, they give you a key card. The key card proves you're a guest.

**Authorization** is what your key card can open. A regular guest's key opens their room. A staff key opens the utility closet. A manager's key opens everything. Same hotel, same building — different access.

The front desk is authentication. The doors are authorization.

---

## What Breaks When You Mix Them

Here are two real bugs that happen when auth and authz are conflated:

**Bug 1: "Only logged-in users can do this" misused as a permission check**

A developer puts `if (!req.user) return 401` on the "delete product" endpoint. Now any logged-in user can delete products. Logging in (authentication) doesn't mean you're an admin (authorization).

**Bug 2: "Checking the role" in the wrong place**

A developer puts `if (req.user.role !== 'admin')` inside the handler function body, but the middleware chain has already attached the wrong user because a token was reused incorrectly. Auth and authz are tangled, so neither works correctly.

**The correct separation:**
- Authentication middleware runs first: "Is there a valid token? Who does it belong to?"
- Authorization middleware/checks run second: "Given this user, are they allowed to do this specific thing?"

They are always separate. One fires after the other. Neither knows about the other's concerns.

---

## The System We're Building

Our system has three distinct layers:

```
Request comes in
    ↓
1. Auth Middleware (authenticate)
   → Is there a valid JWT?
   → Does it belong to a real user who isn't deleted?
   → Attaches user object to request
   → Returns 401 if no/invalid token
    ↓
2. RBAC Middleware (requireRole, requirePermission)
   → Does this user's role have the permission to call this endpoint?
   → Returns 403 if not
    ↓
3. ABAC Check (in handler or policy layer)
   → Does this user own this resource?
   → Is their subscription active?
   → Are they within the allowed time window?
   → Returns 403 if not
    ↓
4. Handler
   → Business logic runs
```

Layer 1 = Authentication.
Layers 2 and 3 = Authorization.

They never merge. Layer 1 never checks roles. Layers 2 and 3 never re-verify the token.

---

## HTTP Status Codes for Auth

These are frequently confused:

**401 Unauthorized** — You are not authenticated. There's no token, or the token is invalid/expired. The name is misleading — it should be called "Unauthenticated." Fix it by logging in.

**403 Forbidden** — You are authenticated (we know who you are) but you don't have permission to do this. Fix it by getting a different role, or you simply can't do this at all.

Returning 401 when you mean 403, or 403 when you mean 401, creates confusing behavior for clients. A client that receives 401 knows to redirect to login. A client that receives 403 knows to show an "Access Denied" page.
