# Lesson 2.2 — JWT Tokens

## The Problem JWT Solves

Traditional authentication uses **sessions**: when you log in, the server creates a session record in the database and sends you a session ID (stored in a cookie). On every request, the server looks up that session ID in the database to find out who you are.

This works, but it means every single request hits the database just to answer "who is making this request?" Under load, that's a lot of database reads.

**JWT (JSON Web Token)** solves this by encoding the user's identity directly in the token itself, in a way that can't be tampered with. The server doesn't need to look anything up — it just reads the token.

JWT is pronounced "jot." Knowing this makes you sound like you've been in the industry for a while.

---

## What a JWT Actually Is

A JWT is three base64-encoded pieces joined by dots:

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ1c2VyX2lkIjoiYWJjMTIzIiwicm9sZSI6Im1lbWJlciIsImlhdCI6MTcxNjkwMDAwMCwiZXhwIjoxNzE2OTAwOTAwfQ.sFlKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
```

Split on the dots:
- **Part 1 (Header):** `eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9`
- **Part 2 (Payload):** `eyJ1c2VyX2lkIjoiYWJjMTIzIiwicm9sZSI6Im1lbWJlciIsImlhdCI6MTcxNjkwMDAwMCwiZXhwIjoxNzE2OTAwOTAwfQ`
- **Part 3 (Signature):** `sFlKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c`

**Header** (decoded): tells you which algorithm was used to create the signature
```json
{ "alg": "HS256", "typ": "JWT" }
```

**Payload** (decoded): the claims — the data stored in the token
```json
{
  "user_id": "abc123",
  "role": "member",
  "iat": 1716900000,    // issued at (Unix timestamp)
  "exp": 1716900900     // expires at (Unix timestamp)
}
```

**Signature**: the header and payload run through a cryptographic function with your `JWT_SECRET`. This is what makes the token tamper-proof.

---

## Why It Can't Be Tampered With

If an attacker changes the payload (e.g., changes `"role": "member"` to `"role": "admin"`), the signature becomes invalid. When your server verifies the token, it recomputes the signature from the received header + payload using your secret, and compares it to the received signature. They won't match. The token is rejected.

The attacker doesn't know your `JWT_ACCESS_SECRET`, so they can't generate a valid signature for their modified payload.

**Important:** The payload is NOT encrypted. It's base64-encoded, which anyone can decode. Never put sensitive data in a JWT payload — no passwords, no credit card numbers. Only put data needed for identification: user ID, role, maybe org ID.

## Access Tokens vs Refresh Tokens

We use two types of tokens, not one. Here's why:

**Access Token:**
- Short-lived (15 minutes)
- Sent with every API request in the `Authorization` header
- Used to authenticate requests
- If stolen, expires quickly

**Refresh Token:**
- Long-lived (30 days)
- Sent only to the `/auth/refresh` endpoint
- Used to get a new access token when the old one expires
- If stolen, it's worse — but it's stored more carefully and rotated

The pattern:
1. User logs in → receives access token (15m) + refresh token (30d)
2. User makes API requests with access token
3. Access token expires → client silently sends refresh token to `/auth/refresh`
4. Server returns new access token (and new refresh token — rotation)
5. Client continues without user noticing

If a refresh token is used, it's immediately invalidated and replaced with a new one. This is called **refresh token rotation**. If an old refresh token is used after it's been rotated, it's a signal that someone stole the old token — you can invalidate the entire token family.

---

## Where to Store Tokens

This is where many applications make a security mistake.

**localStorage**: Common but bad. JavaScript on the page can read localStorage. Any cross-site scripting (XSS) attack — where malicious JavaScript runs on your page — can steal the token.

**`httpOnly` cookies**: Better. The `httpOnly` flag prevents JavaScript from reading the cookie. Browsers still send the cookie on every request automatically. Combine with `SameSite=Strict` to prevent cross-site request forgery (CSRF).

**For this course:**
- **Access token**: Returned in the JSON response body, stored in memory by the client (not localStorage, not cookies). Sent in the `Authorization: Bearer {token}` header.
- **Refresh token**: Stored in an `httpOnly` cookie.

This is a secure compromise that works for both browser and mobile clients.

## The Token Flow in Code (Node.js)

```javascript
// utils/tokens.js
import jwt from 'jsonwebtoken'
import { config } from '../config.js'

export function generateAccessToken(userId, role) {
  return jwt.sign(
    { user_id: userId, role },
    config.auth.accessSecret,
    { expiresIn: config.auth.accessExpiresIn }
  )
}

export function generateRefreshToken(userId) {
  return jwt.sign(
    { user_id: userId },
    config.auth.refreshSecret,
    { expiresIn: config.auth.refreshExpiresIn }
  )
}

export function verifyAccessToken(token) {
  // Throws if invalid or expired
  return jwt.verify(token, config.auth.accessSecret)
}

export function verifyRefreshToken(token) {
  return jwt.verify(token, config.auth.refreshSecret)
}
```

```javascript
// routes/auth.js — login handler (simplified)
export async function login(req, res) {
  const { email, password } = req.body
  
  const user = await db.users.findByEmail(email)
  if (!user) {
    return res.status(401).json({
      error: { code: 'INVALID_CREDENTIALS', message: 'Invalid email or password.' }
    })
  }
  
  const passwordValid = await bcrypt.compare(password, user.password_hash)
  if (!passwordValid) {
    return res.status(401).json({
      error: { code: 'INVALID_CREDENTIALS', message: 'Invalid email or password.' }
    })
  }
  
  // Get user's role
  const role = await db.userRoles.getPrimaryRole(user.id)
  
  const accessToken = generateAccessToken(user.id, role.name)
  const refreshToken = generateRefreshToken(user.id)
  
  // Store refresh token (hashed) in DB so we can invalidate it on logout
  await db.refreshTokens.create({
    user_id: user.id,
    token_hash: await bcrypt.hash(refreshToken, 10),
    expires_at: new Date(Date.now() + 30 * 24 * 60 * 60 * 1000), // 30 days
  })
  
  // Set refresh token as httpOnly cookie
  res.cookie('refresh_token', refreshToken, {
    httpOnly: true,
    secure: config.nodeEnv === 'production',  // HTTPS only in prod
    sameSite: 'strict',
    maxAge: 30 * 24 * 60 * 60 * 1000,        // 30 days in ms
  })
  
  return res.json({
    user: { id: user.id, email: user.email, display_name: user.display_name, role: role.name },
    access_token: accessToken,
  })
}
```

## The Mistake Everyone Makes: Storing Role in the Token

Notice the access token stores the user's `role`. This is a common pattern, but it has a subtle problem: if you change a user's role, their existing access token still has the old role until it expires.

For a 15-minute access token, this is acceptable — the worst case is 15 minutes of wrong role. For a 30-minute or 1-hour token, it becomes a real problem (you could demote an admin and they'd still have admin access for an hour).

**Options:**
1. Keep the access token short (15 minutes) and accept the delay
2. Don't store role in the token — look it up from the database on every request (slower but always correct)
3. Maintain a token blocklist and add the old token when roles change (complex)

For this course, option 1 is the right tradeoff: 15-minute access tokens, role stored in the token for performance.

## Summary

| Concept | Plain English |
|---------|--------------|
| JWT | A signed token that proves identity without hitting the database |
| Header | Which algorithm signed this token |
| Payload | The data stored in the token (user ID, role) |
| Signature | Cryptographic proof the payload wasn't tampered with |
| Access token | Short-lived (15m), sent on every request |
| Refresh token | Long-lived (30d), used only to get new access tokens |
| `httpOnly` cookie | Cookie JavaScript can't read — safer for refresh tokens |
| Token rotation | Invalidating a refresh token after each use |
