# Lesson 2.3 — Password Hashing

## Why You Never Store Plain Passwords

If your database is breached and you stored plain passwords, every user's account on every website where they reused that password is compromised. This has happened to hundreds of major companies. It's one of the most damaging security failures a company can have.

The solution: don't store the password. Store a **hash** of the password — a transformation that can only go one direction.

---

## What Hashing Is (Plain English)

A hash function takes an input of any length and produces a fixed-length output. The same input always produces the same output. But you can't reverse it — you can't take the output and get back the input.

```
"mysecretpassword" → hash function → "a3f8c2d9e4b1..."
```

When a user logs in:
1. They send their password
2. You hash it using the same function
3. You compare the result to the stored hash
4. If they match, the password is correct

You never see the original password again after registration. Even you, the developer, can't look up a user's password.

---

## Why Regular Hash Functions Aren't Enough

You might think: "SHA-256 is a hash function. Why not use that?"

Because SHA-256 is fast. Very fast. An attacker with the hash can try billions of passwords per second (this is called a **brute-force** or **dictionary attack**). Modern GPUs can compute 10 billion SHA-256 hashes per second.

**Password hashing algorithms** (bcrypt, argon2, scrypt) are intentionally slow. They're designed to take time — configurable time. An attacker still has to try every possible password, but each try takes 100ms instead of 0.0000001ms.

---

## bcrypt Explained

bcrypt is the most widely used password hashing algorithm. It has three key properties:

### 1. Cost factor (rounds)

bcrypt takes a "cost factor" (also called "rounds" or "work factor") that controls how slow it is. The cost factor of 12 means bcrypt runs 2^12 = 4,096 iterations of an internal function.

At cost 12 on a modern machine:
- Hashing a password takes ~100-300ms
- An attacker trying to crack your hashed database: ~3-10 hashes per second per machine

If computers get faster, you increase the cost factor. The algorithm scales.

```javascript
// Cost 10: ~65ms per hash
// Cost 12: ~250ms per hash (good for production)
// Cost 8: ~16ms per hash (good for tests — faster tests)
await bcrypt.hash("password", 12)
```

### 2. Salt

A **salt** is random data mixed into the password before hashing. bcrypt generates a unique salt for every password automatically.

Why does this matter? Without salts, if two users have the same password, they'd have the same hash. An attacker who gets your database could instantly identify everyone with a common password by comparing hashes.

With salts, even two users with the password "password123" have completely different hashes. There's no pattern to exploit.

### 3. The stored hash contains the salt

When bcrypt stores a hash, it includes the salt in the output:
```
$2b$12$LQv3c1yqBWVHxkd0LHAkCOYz6TtxMQJqhN8/LewdBPj/E9PSNLKi6
```

Breakdown:
- `$2b$` — bcrypt version
- `$12$` — cost factor
- `LQv3c1yqBWVHxkd0LHAkCO` — the salt (22 characters)
- `Yz6TtxMQJqhN8/LewdBPj/E9PSNLKi6` — the hash

When verifying, bcrypt extracts the salt from the stored hash automatically. You don't manage salts yourself.

## The Registration Flow

```javascript
// routes/auth.js
import bcrypt from 'bcrypt'
import { config } from '../config.js'
import { generateAccessToken, generateRefreshToken } from '../utils/tokens.js'

export async function register(req, res) {
  const { email, password, display_name } = req.body
  
  // 1. Validate input
  if (!email || !password) {
    return res.status(400).json({
      error: { code: 'MISSING_FIELDS', message: 'Email and password are required.', field: null }
    })
  }
  
  if (password.length < 8) {
    return res.status(400).json({
      error: { code: 'PASSWORD_TOO_SHORT', message: 'Password must be at least 8 characters.', field: 'password' }
    })
  }
  
  // 2. Check for duplicate email
  const existing = await db.users.findByEmail(email.toLowerCase())
  if (existing) {
    return res.status(409).json({
      error: { code: 'EMAIL_EXISTS', message: 'An account with this email already exists.', field: 'email' }
    })
  }
  
  // 3. Hash the password
  const passwordHash = await bcrypt.hash(password, config.auth.bcryptRounds)
  
  // 4. Create the user
  const user = await db.users.create({
    email: email.toLowerCase(),
    password_hash: passwordHash,
    display_name: display_name ?? null,
  })
  
  // 5. Create Stripe customer (we'll cover this in Part 5)
  const stripeCustomer = await stripe.customers.create({
    email: user.email,
    name: user.display_name,
    metadata: { user_id: user.id },
  })
  
  await db.users.update(user.id, { stripe_customer_id: stripeCustomer.id })
  
  // 6. Assign default role
  const memberRole = await db.roles.findByName('member')
  await db.userRoles.create({ user_id: user.id, role_id: memberRole.id })
  
  // 7. Send verification email (we'll cover this later)
  // await emailService.sendVerification(user)
  
  // 8. Generate tokens and return
  const accessToken = generateAccessToken(user.id, 'member')
  const refreshToken = generateRefreshToken(user.id)
  
  res.cookie('refresh_token', refreshToken, {
    httpOnly: true,
    secure: config.nodeEnv === 'production',
    sameSite: 'strict',
    maxAge: 30 * 24 * 60 * 60 * 1000,
  })
  
  return res.status(201).json({
    user: { id: user.id, email: user.email, display_name: user.display_name },
    access_token: accessToken,
  })
}
```

## The Login Flow

```javascript
export async function login(req, res) {
  const { email, password } = req.body
  
  // 1. Find the user
  // Note: always give the SAME error whether email or password is wrong
  // If you say "email not found" for bad emails, attackers can enumerate valid emails
  const user = await db.users.findByEmail(email?.toLowerCase())
  if (!user || user.deleted_at) {
    return res.status(401).json({
      error: { code: 'INVALID_CREDENTIALS', message: 'Invalid email or password.' }
    })
  }
  
  // 2. Verify password
  const passwordValid = await bcrypt.compare(password, user.password_hash)
  if (!passwordValid) {
    return res.status(401).json({
      error: { code: 'INVALID_CREDENTIALS', message: 'Invalid email or password.' }
    })
  }
  
  // 3. Update last_login_at
  await db.users.update(user.id, { last_login_at: new Date() })
  
  // 4. Get role
  const role = await db.userRoles.getPrimaryRole(user.id)
  
  // 5. Generate tokens
  const accessToken = generateAccessToken(user.id, role.name)
  const refreshToken = generateRefreshToken(user.id)
  
  res.cookie('refresh_token', refreshToken, {
    httpOnly: true,
    secure: config.nodeEnv === 'production',
    sameSite: 'strict',
    maxAge: 30 * 24 * 60 * 60 * 1000,
  })
  
  return res.json({
    user: { id: user.id, email: user.email, display_name: user.display_name, role: role.name },
    access_token: accessToken,
  })
}
```

## The Security Detail That Most Tutorials Skip

Notice: when the email doesn't exist AND when the password is wrong, we return the exact same error: `INVALID_CREDENTIALS`.

**Never tell the caller which part was wrong.**

If you return "email not found" for invalid emails, an attacker can run through a list of emails and find which ones have accounts. This is called **user enumeration** and it's a real attack.

The same error for both cases prevents this. Yes, it's slightly worse UX. It's significantly better security.

---

## bcrypt vs argon2

For new projects, `argon2` is technically better than bcrypt — it's the winner of the Password Hashing Competition (2015) and is more resistant to GPU-based attacks. But bcrypt has been battle-tested for decades and is universally supported.

This course uses bcrypt. If you want to use argon2 in your own projects:
```javascript
import argon2 from 'argon2'

const hash = await argon2.hash(password)
const valid = await argon2.verify(hash, password)
```

The concepts are identical. The algorithm is different. Either is acceptable.

|---------|--------------|
| Hash function | One-way transformation — you can't reverse it |
| Salt | Random data mixed in so identical passwords produce different hashes |
