# Lesson 3.1 — RBAC: Role-Based Access Control

## The Mental Model

Imagine a company. Everyone has a job title. The job title determines what you're allowed to do:

- An **intern** can read documents but can't approve them
- An **employee** can create and submit documents
- A **manager** can approve documents
- An **IT admin** can access everything

This is RBAC. Your **role** (job title) determines your **permissions** (what you can do). It doesn't matter who you specifically are — it matters what role you hold.

In code: roles are stored in a database, permissions are assigned to roles, and middleware checks whether the requesting user's role has the required permission.

---

## Our Roles

For the course project:

| Role | Who it's for | What they can do |
|------|-------------|-----------------|
| `guest` | Not logged in | Read public content only |
| `member` | Registered user | Purchase products, manage own subscription, view own data |
| `support` | Customer support agent | View user data and subscriptions to help customers |
| `admin` | Platform administrator | Everything: change prices, manage users, view all data |

These roles form a rough hierarchy, but they're not strictly hierarchical. A support agent can see things a member can't, but they can't change prices (only admins can). It's not a simple "admin > support > member > guest" ladder.

## The Database Structure

```sql
-- Roles (seeded, not created by users)
INSERT INTO roles (name, description) VALUES
  ('guest',   'Unauthenticated visitor'),
  ('member',  'Registered user'),
  ('support', 'Customer support agent'),
  ('admin',   'Platform administrator');

-- Permissions (seeded)
INSERT INTO permissions (name, description) VALUES
  -- Products
  ('products:read',          'View products'),
  ('products:write',         'Create and update products'),
  ('products:delete',        'Delete products'),
  -- Prices  
  ('prices:read',            'View price history'),
  ('prices:write',           'Create new prices'),
  -- Plans
  ('plans:read',             'View plans'),
  ('plans:write',            'Create and update plans'),
  -- Subscriptions
  ('subscriptions:read_own', 'Read own subscription'),
  ('subscriptions:read_all', 'Read all subscriptions'),
  ('subscriptions:manage',   'Change subscription plans'),
  ('subscriptions:cancel',   'Cancel a subscription'),
  -- Users
  ('users:read_own',         'Read own user data'),
  ('users:read_all',         'Read all user data'),
  ('users:manage',           'Update user accounts and roles'),
  ('users:delete',           'Soft-delete user accounts'),
  -- Payments
  ('payments:read_own',      'View own payment history'),
  ('payments:read_all',      'View all payment history'),
  -- Coupons
  ('coupons:read',           'View coupons'),
  ('coupons:write',          'Create and manage coupons'),
  ('coupons:use',            'Apply coupons at checkout'),
  -- Reports
  ('reports:read',           'View admin reports and analytics'),
  -- Audit logs
  ('audit_logs:read',        'View audit logs');
```

Now assign permissions to roles:

```sql
-- guest: can read public content (enforced at route level, not permission level)
-- (no permissions needed — public endpoints have no auth middleware)

-- member permissions
INSERT INTO role_permissions (role_id, permission_id)
SELECT r.id, p.id FROM roles r, permissions p
WHERE r.name = 'member' AND p.name IN (
  'products:read',
  'plans:read',
  'subscriptions:read_own',
  'subscriptions:cancel',
  'users:read_own',
  'payments:read_own',
  'coupons:use'
);

-- support permissions
INSERT INTO role_permissions (role_id, permission_id)
SELECT r.id, p.id FROM roles r, permissions p
WHERE r.name = 'support' AND p.name IN (
  'products:read',
  'plans:read',
  'subscriptions:read_all',
  'users:read_all',
  'payments:read_all',
  'coupons:read'
);

-- admin permissions (everything)
INSERT INTO role_permissions (role_id, permission_id)
SELECT r.id, p.id FROM roles r, permissions p
WHERE r.name = 'admin';
-- Admins get every permission
```

## The RBAC Middleware

```javascript
// middleware/requireRole.js

// Checks if the user has one of the allowed roles
export function requireRole(...roles) {
  return (req, res, next) => {
    // authenticate middleware must run first — req.user must exist
    if (!req.user) {
      return res.status(401).json({
        error: { code: 'NOT_AUTHENTICATED', message: 'Authentication required.' }
      })
    }
    
    if (!roles.includes(req.user.role)) {
      return res.status(403).json({
        error: {
          code: 'INSUFFICIENT_ROLE',
          message: `This action requires one of the following roles: ${roles.join(', ')}.`
        }
      })
    }
    
    next()
  }
}
```

```javascript
// middleware/requirePermission.js

// Checks if the user's role has a specific permission
export function requirePermission(permission) {
  return async (req, res, next) => {
    if (!req.user) {
      return res.status(401).json({
        error: { code: 'NOT_AUTHENTICATED', message: 'Authentication required.' }
      })
    }
    
    const hasPermission = await db.rolePermissions.check(req.user.role, permission)
    
    if (!hasPermission) {
      return res.status(403).json({
        error: {
          code: 'INSUFFICIENT_PERMISSION',
          message: 'You do not have permission to perform this action.'
        }
      })
    }
    
    next()
  }
}
```

```javascript
// db/queries/rolePermissions.js
export async function check(roleName, permissionName) {
  const result = await db.query(`
    SELECT 1
    FROM role_permissions rp
    JOIN roles r ON r.id = rp.role_id
    JOIN permissions p ON p.id = rp.permission_id
    WHERE r.name = $1
      AND p.name = $2
    LIMIT 1
  `, [roleName, permissionName])
  
  return result.rows.length > 0
}
```

## Using the Middleware on Routes

```javascript
// routes/products.js
import { authenticate } from '../middleware/authenticate.js'
import { requirePermission } from '../middleware/requirePermission.js'
import * as productHandlers from '../handlers/products.js'

// Public — no auth needed
router.get('/products', productHandlers.list)
router.get('/products/:id', productHandlers.getOne)

// Create product — requires products:write permission (only admins have it)
router.post('/products',
  authenticate,
  requirePermission('products:write'),
  productHandlers.create
)

// Update product — requires products:write
router.patch('/products/:id',
  authenticate,
  requirePermission('products:write'),
  productHandlers.update
)

// Add a new price — requires prices:write
router.post('/products/:id/prices',
  authenticate,
  requirePermission('prices:write'),
  productHandlers.addPrice
)

// View price history — requires prices:read
router.get('/products/:id/prices',
  authenticate,
  requirePermission('prices:read'),
  productHandlers.getPriceHistory
)
```

## The Permission Check Query — Performance Note

The `requirePermission` middleware hits the database on every request. For high-traffic applications, this adds latency.

**Optimization options:**
1. **Cache permissions per role in memory** (roles don't change often — cache for 5 minutes)
2. **Store the user's permissions in the JWT** (works for simple permission sets, but JWTs get large)
3. **Accept the database hit** (for most applications, this is fine — it's a simple indexed query)

For this course, we accept the database hit. The query is fast (indexed), and caching adds complexity.

## What RBAC Handles Well

- "Only admins can change prices" ✓
- "Only admins can view audit logs" ✓
- "Only members and admins can purchase" ✓
- "Only support and admins can view all subscriptions" ✓

## What RBAC Can't Handle

- "A member can edit their OWN profile but not another member's profile" ✗
- "A member can only access premium content if their subscription is active" ✗
- "A support agent can only view customers assigned to them" ✗

These require attributes — context about the specific request. That's ABAC, covered in the next lesson.
