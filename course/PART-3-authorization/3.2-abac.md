# Lesson 3.2 — ABAC: Attribute-Based Access Control

## Where RBAC Falls Short

In Lesson 3.1, we saw that RBAC handles role-level access well. But there's a class of problems it can't solve.

**The profile edit problem:**
Both Alice and Bob have the `member` role. RBAC says: members can edit profiles. But Alice should NOT be able to edit Bob's profile. RBAC has no concept of "this profile belongs to this user."

**The subscription gate problem:**
Alice has the `member` role but her subscription expired. She should not be able to access premium content. RBAC has no concept of subscription state.

**The support agent problem:**
All support agents have the `support` role. But in some companies, support agents are assigned to specific customers. Agent Sarah can view Customer A's data, but not Customer B's. RBAC has no concept of assignment.

These are **attribute-based** problems. Access depends not just on role, but on attributes — properties of the user, the resource being accessed, and the context of the request.

---

## The ABAC Model

ABAC evaluates access based on four types of attributes:

| Attribute type | What it describes | Examples |
|---------------|-------------------|---------|
| **Subject** | The user making the request | role, subscription status, organization ID, assigned customers |
| **Resource** | The thing being accessed | owner_id, organization_id, is_locked, created_at |
| **Action** | What they're trying to do | read, write, delete, cancel |
| **Environment** | The context | current time, request IP, subscription active? |

An ABAC **policy** is a function that evaluates these attributes and returns `true` (allowed) or `false` (denied).

---

## Writing ABAC Policies

Policies are plain functions. They receive the subject (user), resource, action, and environment, and return whether the action is allowed.

```javascript
// policies/index.js

/**
 * Can the user edit the given profile?
 * Rule: user can edit their own profile, admins can edit any profile,
 *       but nobody can edit the organization owner's profile (except the owner themselves)
 */
export function canEditProfile(user, targetUser) {
  // Admins can edit anyone except org owners (unless admin IS the org owner)
  if (user.role === 'admin') {
    if (targetUser.is_org_owner && user.id !== targetUser.id) return false
    return true
  }
  
  // Members can only edit their own profile
  return user.id === targetUser.id
}


/**
 * Can the user access premium content?
 * Rule: subscription must be 'active' or 'trialing'
 */
export function canAccessPremiumContent(user, subscription) {
  if (user.role === 'admin') return true  // Admins always have access
  
  if (!subscription) return false
  
  return ['active', 'trialing'].includes(subscription.status)
}


/**
 * Can the user view the given subscription?
 * Rule: members see only their own, support sees all, admins see all
 */
export function canViewSubscription(user, subscription) {
  if (user.role === 'admin') return true
  if (user.role === 'support') return true
  
  // Members can only see their own subscription
  return subscription.user_id === user.id
}


/**
 * Can the user cancel the given subscription?
 * Rule: owner can cancel their own, admins can cancel any
 *       Cannot cancel if already canceled
 */
export function canCancelSubscription(user, subscription) {
  if (subscription.status === 'canceled') return false
  if (user.role === 'admin') return true
  
  return subscription.user_id === user.id
}


/**
 * Can the user view the given invoice?
 * Rule: admins and support see all, members see only their own
 */
export function canViewInvoice(user, invoice) {
  if (user.role === 'admin' || user.role === 'support') return true
  return invoice.user_id === user.id
}


/**
 * Can the user delete the given user account?
 * Rule: only admins, cannot delete yourself, cannot delete org owner
 */
export function canDeleteUser(actor, targetUser) {
  if (actor.role !== 'admin') return false
  if (actor.id === targetUser.id) return false      // Can't delete yourself
  if (targetUser.is_org_owner) return false         // Can't delete org owner
  return true
}
```

## Using Policies in Handlers

Policies are called inside the handler, after the resource has been fetched from the database:

```javascript
// handlers/users.js
import { canEditProfile, canDeleteUser } from '../policies/index.js'

export async function updateUser(req, res) {
  const { id } = req.params
  const actor = req.user  // set by authenticate middleware
  
  // Fetch the resource
  const targetUser = await db.users.findById(id)
  if (!targetUser || targetUser.deleted_at) {
    return res.status(404).json({
      error: { code: 'USER_NOT_FOUND', message: 'User not found.' }
    })
  }
  
  // ABAC policy check
  if (!canEditProfile(actor, targetUser)) {
    return res.status(403).json({
      error: {
        code: 'FORBIDDEN',
        message: 'You do not have permission to edit this profile.'
      }
    })
  }
  
  // Proceed with the update
  const updated = await db.users.update(id, req.body)
  return res.json({ user: updated })
}
```

```javascript
// handlers/subscriptions.js
import { canCancelSubscription } from '../policies/index.js'

export async function cancelSubscription(req, res) {
  const { id } = req.params
  const actor = req.user
  
  const subscription = await db.subscriptions.findById(id)
  if (!subscription || subscription.deleted_at) {
    return res.status(404).json({
      error: { code: 'SUBSCRIPTION_NOT_FOUND', message: 'Subscription not found.' }
    })
  }
  
  if (!canCancelSubscription(actor, subscription)) {
    // If it's already canceled, give a specific error
    if (subscription.status === 'canceled') {
      return res.status(409).json({
        error: { code: 'ALREADY_CANCELED', message: 'This subscription is already canceled.' }
      })
    }
    return res.status(403).json({
      error: { code: 'FORBIDDEN', message: 'You cannot cancel this subscription.' }
    })
  }
  
  // Call Stripe to cancel (covered in Part 5)
  // ...
}
```

## The Policy Helper Middleware (For Cleaner Routes)

For policies that can be evaluated with just the route parameters (before fetching the resource), you can use a middleware pattern:

```javascript
// middleware/requirePolicy.js
export function requirePolicy(policyFn, ...resourceFetchers) {
  return async (req, res, next) => {
    // Fetch all needed resources
    const resources = await Promise.all(
      resourceFetchers.map(fetcher => fetcher(req))
    )
    
    const allowed = await policyFn(req.user, ...resources)
    
    if (!allowed) {
      return res.status(403).json({
        error: { code: 'FORBIDDEN', message: 'Access denied.' }
      })
    }
    
    // Attach fetched resources to req so handler doesn't re-fetch
    req.resources = resources
    next()
  }
}
```

Usage:
```javascript
// routes/subscriptions.js
router.patch('/subscriptions/:id/cancel',
  authenticate,
  requirePermission('subscriptions:cancel'),                    // RBAC: must have permission
  requirePolicy(                                                // ABAC: must own it
    canCancelSubscription,
    (req) => db.subscriptions.findById(req.params.id)
  ),
  cancelSubscription
)
```

## Subscription Gate Middleware

The subscription status check is so common it deserves its own middleware:

```javascript
// middleware/requireActiveSubscription.js
export async function requireActiveSubscription(req, res, next) {
  if (req.user.role === 'admin') return next()  // Admins bypass this
  
  const subscription = await db.subscriptions.findActiveByUserId(req.user.id)
  
  if (!subscription || !['active', 'trialing'].includes(subscription.status)) {
    return res.status(403).json({
      error: {
        code: 'SUBSCRIPTION_REQUIRED',
        message: 'An active subscription is required to access this content.',
        subscription_status: subscription?.status ?? 'none',
      }
    })
  }
  
  req.subscription = subscription  // Attach for handlers to use
  next()
}
```

Usage:
```javascript
// A premium content endpoint
router.get('/content/premium',
  authenticate,
  requirePermission('content:read'),          // RBAC
  requireActiveSubscription,                   // ABAC (subscription state)
  getPremiumContent
)
```

## Summary of the Policy Pattern

Every ABAC check follows the same pattern:

1. **Fetch the resource** from the database
2. **Call the policy function** with (actor, resource)
3. **Return 403 if denied**, continue if allowed

Policies are:
- **Pure functions** — given the same inputs, always return the same result
- **Easy to test** — just call the function with different user/resource combinations
- **Centralized** — all business rules in one place (`policies/index.js`)
