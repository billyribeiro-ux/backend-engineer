# Lesson 3.3 — When to Use RBAC, ABAC, or Both

## The Decision Framework

This is the lesson where we make the rules concrete and practical. By the end, you'll have a mental framework you can apply to any authorization problem in any system.

---

## The Three Cases

### Case 1: Use RBAC alone

**When:** Access depends only on who the user is (their role), not on what they're touching or the current state of anything.

**Characteristics:**
- The answer is the same for all users of that role, regardless of context
- No need to fetch the resource to make the decision
- Can be enforced entirely in middleware before the handler runs

**Examples:**
```
"Only admins can change prices"
→ If your role is admin: allowed. If not: denied.
→ Doesn't matter which price, whose price, when it was created.
→ Pure RBAC.

"Only admins can view audit logs"
→ If admin: allowed. If not: denied.
→ Pure RBAC.

"Only admins and support agents can view all user accounts"
→ If admin or support: allowed. If not: denied.
→ Pure RBAC.
```

**Code:**
```javascript
router.post('/prices',
  authenticate,
  requirePermission('prices:write'),  // RBAC — done
  createPrice
)
```

---

### Case 2: Use ABAC alone

**When:** Access doesn't depend on role but depends entirely on the relationship between the user and the resource, or on resource/environment state.

**Characteristics:**
- Any authenticated user with the right relationship can do this
- The role doesn't restrict it — just the context
- Need to fetch the resource to make the decision

**Examples:**
```
"A user can read their own activity log"
→ Any authenticated user can do this — as long as it's THEIR log.
→ No role discrimination — a member and an admin both can see their own.
→ Pure ABAC (ownership check).

"A user can update their own email address"
→ Any authenticated user can update their own email — if it's their account.
→ Pure ABAC.
```

**Code:**
```javascript
router.get('/activity-logs/me',
  authenticate,
  // No requirePermission — any authenticated user can see their own
  requirePolicy(
    (user, log) => log.user_id === user.id,
    (req) => db.activityLogs.findForUser(req.user.id)
  ),
  getMyActivityLog
)
```

In practice, Case 2 is less common than it looks. Most systems have at least an implicit role requirement ("you must be a member to do this"). Pure ABAC without any role check is rare.

---

### Case 3: Use Both (RBAC + ABAC)

**When:** You need a role gate AND contextual rules. Most real-world authorization falls here.

**Characteristics:**
- Only certain roles are even eligible (RBAC gate)
- Among eligible users, access depends on context (ABAC refinement)
- Both checks must pass

This is the hospital example from Lesson 0.3, fully realized.

**Examples from our course project:**

**Edit a user profile:**
```
RBAC: Must be member or admin (guests and support cannot edit profiles)
ABAC: Members can only edit their own profile; admins can edit any profile
      except they cannot edit the org owner's profile (unless they ARE the org owner)

Code:
router.patch('/users/:id',
  authenticate,
  requirePermission('users:manage'),        // RBAC: must have manage permission
  getTargetUserMiddleware,                  // Fetch resource
  requirePolicy(canEditProfile),            // ABAC: ownership + org owner protection
  updateUser
)
```

**Cancel a subscription:**
```
RBAC: Must have subscriptions:cancel permission (members and admins have this)
ABAC: Members can only cancel their OWN subscription
      Cannot cancel an already-canceled subscription (resource state)
      Admins can cancel any subscription

Code:
router.patch('/subscriptions/:id/cancel',
  authenticate,
  requirePermission('subscriptions:cancel'),  // RBAC
  requirePolicy(canCancelSubscription, ...),   // ABAC
  cancelSubscription
)
```

**View a subscription:**
```
RBAC: Must have subscriptions:read_own OR subscriptions:read_all
ABAC: Users with read_own can only see their own subscriptions
      Users with read_all (support, admin) see everything

Code:
router.get('/subscriptions/:id',
  authenticate,
  requirePermission('subscriptions:read_own'),  // At minimum, this role needed
  requirePolicy(canViewSubscription, ...),       // ABAC refines it further
  getSubscription
)
```

**Access premium content:**
```
RBAC: Must have the 'member' role
ABAC: Subscription must be 'active' or 'trialing' (environment/state attribute)

Code:
router.get('/content/premium',
  authenticate,
  requirePermission('content:read'),      // RBAC: member role gate
  requireActiveSubscription,              // ABAC: subscription state gate
  getPremiumContent
)
```

## Real-World Example: Hospitals

This is worth fully spelling out because it's the canonical example of RBAC + ABAC in a safety-critical system.

**The scenario:** A hospital uses software to manage patient records.

**RBAC defines what roles can do:**
```
doctor      → can read/write patient records
nurse       → can read patient records, write vital signs
billing     → can read billing records, cannot read medical records
receptionist → can read patient names and appointment times only
IT admin    → can access everything for system maintenance
```

**RBAC alone is insufficient because:**
- A cardiologist doesn't need access to psychiatric records
- A surgeon on the orthopedic wing shouldn't see ICU records
- A doctor from Hospital A shouldn't see records from Hospital B

**ABAC adds the contextual rules:**
```
doctor can read patient records IF:
  - patient is assigned to this doctor's department AND
  - doctor has an active shift OR is on call AND
  - the record type is within this doctor's specialty
  
nurse can write vital signs IF:
  - patient is assigned to nurse's unit AND
  - nurse has an active shift
```

**The combined check (RBAC + ABAC):**
```
1. Is this user's role 'doctor'? (RBAC) → if not, deny
2. Is this patient in the doctor's department? (ABAC) → if not, deny
3. Is the doctor currently on shift? (ABAC) → if not, deny
4. Is the record type within the doctor's specialty? (ABAC) → if not, deny
5. Allow
```

Every layer reduces the attack surface. RBAC removes 95% of unauthorized access by role. ABAC handles the remaining 5% that role-based rules can't express.

## The Decision Tree

When you encounter a new authorization requirement, ask these questions in order:

```
Q1: Can any authenticated user of this type do this?
    (regardless of which specific resource or what state it's in)
    
    Yes → RBAC only (requirePermission)
    No  → Continue to Q2

Q2: Can any authenticated user do this,
    as long as they own the resource?
    
    Yes → ABAC only (requirePolicy with ownership check)
    No  → Continue to Q3

Q3: Is there a role requirement AND a contextual rule?

    Yes → Both RBAC + ABAC
          - requirePermission (role gate)
          - requirePolicy (contextual gate)
```

## The Golden Rule

**RBAC tells you who CAN. ABAC tells you who CAN given the situation.**

Start with RBAC to restrict by role. Add ABAC when role alone isn't enough to express the rule.

Never skip the role check when one is needed (security risk). Never add an ABAC check that duplicates what RBAC already enforces (complexity for no gain).
