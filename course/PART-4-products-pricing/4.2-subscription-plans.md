# Lesson 4.2 — Subscription Plans

## Plans vs Products

A **product** is something you buy once. A **plan** is something you pay for repeatedly on a schedule.

Plans have:
- A billing interval (`month`, `year`)
- An interval count (every 1 month, every 3 months, every 12 months)
- A price (which follows the same versioning rules as products)
- A trial period option

For our course project, we have three plan tiers:
- **Monthly** — billed every 1 month
- **Quarterly** — billed every 3 months (same `month` interval, `interval_count = 3`)
- **Yearly** — billed every 1 year

## Creating a Plan

```javascript
// handlers/plans.js

export async function createPlan(req, res) {
  const { name, interval, interval_count = 1, amount_cents, currency = 'usd' } = req.body
  
  const validIntervals = ['day', 'week', 'month', 'year']
  if (!validIntervals.includes(interval)) {
    return res.status(400).json({
      error: { code: 'INVALID_INTERVAL', message: `interval must be one of: ${validIntervals.join(', ')}` }
    })
  }
  
  // Create in DB (transaction: plan + first price)
  const result = await db.transaction(async (client) => {
    const plan = await client.query(`
      INSERT INTO plans (id, name, interval, interval_count)
      VALUES (uuid_generate_v4(), $1, $2, $3)
      RETURNING *
    `, [name, interval, interval_count])
    
    const price = await client.query(`
      INSERT INTO prices (id, plan_id, amount_cents, currency, applies_to, is_current)
      VALUES (uuid_generate_v4(), $1, $2, $3, 'future_members', true)
      RETURNING *
    `, [plan.rows[0].id, amount_cents, currency])
    
    return { plan: plan.rows[0], price: price.rows[0] }
  })
  
  return res.status(201).json(result)
}


export async function listPlans(req, res) {
  const plans = await db.query(`
    SELECT 
      p.id,
      p.name,
      p.interval,
      p.interval_count,
      p.is_active,
      pr.id as price_id,
      pr.amount_cents,
      pr.currency
    FROM plans p
    LEFT JOIN prices pr ON pr.plan_id = p.id AND pr.is_current = true
    WHERE p.deleted_at IS NULL
      AND p.is_active = true
    ORDER BY pr.amount_cents ASC
  `)
  
  return res.json({ plans: plans.rows })
}
```

## Trial Periods

A free trial means: the user starts a subscription but isn't charged until the trial period ends.

Trials are set at the subscription creation time. The key fields:

```sql
subscriptions.status          = 'trialing'
subscriptions.trial_ends_at   = NOW() + INTERVAL '14 days'
```

When the trial ends:
- Stripe automatically charges the user
- Stripe sends `customer.subscription.trial_will_end` webhook 3 days before
- Stripe sends `customer.subscription.updated` webhook when trial becomes active
- Your system updates the subscription status from `trialing` to `active`

**The warning email flow:**
When you receive `customer.subscription.trial_will_end`, you should:
1. Look up the user
2. Queue an email: "Your trial ends in 3 days. Your card will be charged $X."
3. If the user has no payment method on file, urge them to add one

```javascript
// In your webhook handler (Part 5)
case 'customer.subscription.trial_will_end': {
  const stripeSubscription = event.data.object
  
  const subscription = await db.subscriptions.findByStripeId(stripeSubscription.id)
  if (!subscription) break
  
  const user = await db.users.findById(subscription.user_id)
  
  // Queue email notification
  await emailQueue.add('trial-ending', {
    user_id: user.id,
    email: user.email,
    display_name: user.display_name,
    trial_ends_at: new Date(stripeSubscription.trial_end * 1000),
    plan_name: subscription.plan_name,
    amount_cents: subscription.price_amount_cents,
  })
  
  break
}
```

## Subscription Status States

Understanding all possible subscription states is critical. Stripe uses these exactly:

| Status | What it means | User has access? |
|--------|--------------|-----------------|
| `trialing` | In free trial period | Yes |
| `active` | Paying and current | Yes |
| `past_due` | Payment failed, retrying | Yes (grace period) |
| `unpaid` | Payment failed, retries exhausted | No |
| `canceled` | Deliberately canceled | No (after period end) |
| `incomplete` | Initial payment pending | No |
| `incomplete_expired` | Initial payment never completed | No |

For your content access check, the rule is:
```javascript
const ACTIVE_STATUSES = ['active', 'trialing']
// past_due gets a grace period — don't lock them out immediately
// Stripe gives a few days to retry payment
```

Whether to include `past_due` in your access list is a business decision. Many products keep access during `past_due` to give users time to fix their payment method without losing access. We'll give a 3-day grace period.

## The Upgrade/Downgrade Flow

When a user switches plans (e.g., monthly → yearly), Stripe handles the proration (calculating what they owe or are owed for the partial period).

```javascript
export async function changeSubscriptionPlan(req, res) {
  const { id: subscriptionId } = req.params
  const { plan_id } = req.body
  
  const subscription = await db.subscriptions.findById(subscriptionId)
  if (!subscription) {
    return res.status(404).json({ error: { code: 'NOT_FOUND', message: 'Subscription not found.' } })
  }
  
  const newPlan = await db.plans.findById(plan_id)
  const newPrice = await db.prices.findCurrentByPlanId(plan_id)
  
  if (!newPlan || !newPrice) {
    return res.status(404).json({ error: { code: 'PLAN_NOT_FOUND', message: 'Plan not found.' } })
  }
  
  // Tell Stripe to change the plan
  const updatedStripeSubscription = await stripe.subscriptions.update(
    subscription.stripe_subscription_id,
    {
      items: [{
        id: stripeSubscription.items.data[0].id,
        price: newPrice.stripe_price_id,
      }],
      proration_behavior: 'create_prorations',  // Stripe calculates prorated invoice
    }
  )
  
  // Update our local record
  await db.subscriptions.update(subscription.id, {
    plan_id: newPlan.id,
    locked_price_id: newPrice.id,
    status: updatedStripeSubscription.status,
  })
  
  await db.auditLogs.create({
    actor_id: req.user.id,
    action: 'subscription.plan_changed',
    resource_type: 'subscription',
    resource_id: subscription.id,
    metadata: {
      old_plan_id: subscription.plan_id,
      new_plan_id: plan_id,
    }
  })
  
  return res.json({ subscription: await db.subscriptions.findById(subscription.id) })
}
```

## Key Insight: Why Plans Have Their Own Price History

You might wonder: why not just have one flat price per plan (monthly = $19.99, yearly = $179.99)?

Because plans can change price too. If you raise the monthly price from $19.99 to $24.99, some users may be grandfathered at the old monthly price. The same price versioning logic applies.

This is why the `prices` table handles both products (`product_id`) and plans (`plan_id`) — they share the same versioning mechanism.
