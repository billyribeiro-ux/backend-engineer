# Lesson 6.1 — What to Test and What Not to Test

## The Testing Pyramid

There are three levels of tests:

**Unit tests** — Test a single function in isolation. Fast, lots of them. No database, no network.
**Integration tests** — Test multiple components working together. Slower. May use a real database.
**End-to-end tests** — Test the entire system from HTTP request to database. Slowest. Real Stripe test mode.

The pyramid: many unit tests, fewer integration tests, very few end-to-end tests. Each level is slower and more expensive to run. Invert the pyramid and your CI pipeline takes 20 minutes per PR.

---

## What to Unit Test

Unit tests are for **pure functions** — functions that take inputs and return outputs with no side effects (no database, no network, no randomness).

**Test these:**
- Price calculation logic (`applyDiscount`)
- Coupon validation logic (the pure validation, not the DB check)
- Token generation and verification
- ABAC policy functions
- Date/time calculations (trial expiry, grace period)

```javascript
// tests/unit/pricing.test.js
import { applyDiscount } from '../../src/services/coupons.js'

describe('applyDiscount', () => {
  test('applies percent discount correctly', () => {
    expect(applyDiscount(1999, 'percent', 20)).toBe(1599)  // $19.99 - 20% = $15.99
  })
  
  test('applies fixed discount correctly', () => {
    expect(applyDiscount(1999, 'fixed', 500)).toBe(1499)   // $19.99 - $5 = $14.99
  })
  
  test('never returns negative amount', () => {
    expect(applyDiscount(500, 'fixed', 1000)).toBe(0)      // Can't go below $0
  })
  
  test('100% discount results in 0', () => {
    expect(applyDiscount(1999, 'percent', 100)).toBe(0)
  })
})
```

```javascript
// tests/unit/policies.test.js
import { canEditProfile, canCancelSubscription, canViewSubscription } from '../../src/policies/index.js'

describe('canEditProfile', () => {
  test('member can edit own profile', () => {
    const user = { id: 'u1', role: 'member' }
    const target = { id: 'u1', is_org_owner: false }
    expect(canEditProfile(user, target)).toBe(true)
  })
  
  test('member cannot edit another member profile', () => {
    const user = { id: 'u1', role: 'member' }
    const target = { id: 'u2', is_org_owner: false }
    expect(canEditProfile(user, target)).toBe(false)
  })
  
  test('admin can edit any profile', () => {
    const admin = { id: 'a1', role: 'admin' }
    const target = { id: 'u2', is_org_owner: false }
    expect(canEditProfile(admin, target)).toBe(true)
  })
  
  test('admin cannot edit org owner profile (unless is org owner)', () => {
    const admin = { id: 'a1', role: 'admin' }
    const orgOwner = { id: 'o1', is_org_owner: true }
    expect(canEditProfile(admin, orgOwner)).toBe(false)
  })
})

describe('canCancelSubscription', () => {
  test('member can cancel own subscription', () => {
    const user = { id: 'u1', role: 'member' }
    const sub = { user_id: 'u1', status: 'active' }
    expect(canCancelSubscription(user, sub)).toBe(true)
  })
  
  test('cannot cancel already canceled subscription', () => {
    const user = { id: 'u1', role: 'member' }
    const sub = { user_id: 'u1', status: 'canceled' }
    expect(canCancelSubscription(user, sub)).toBe(false)
  })
  
  test('admin can cancel any subscription', () => {
    const admin = { id: 'a1', role: 'admin' }
    const sub = { user_id: 'u2', status: 'active' }
    expect(canCancelSubscription(admin, sub)).toBe(true)
  })
})
```

## What to Integration Test

Integration tests use a real test database. They test that your queries, middleware, and handlers work together correctly.

**Test these:**
- Auth endpoints (register, login, refresh, logout)
- RBAC middleware (role correctly blocks or allows)
- ABAC policies (ownership checks with real data)
- Webhook handlers (with real DB writes)
- Subscription access gates

Use your test database (`DATABASE_TEST_URL`) and reset it between test runs.

```javascript
// tests/integration/auth.test.js
import request from 'supertest'
import app from '../../src/app.js'
import { db } from '../../src/db/index.js'

describe('POST /auth/register', () => {
  beforeEach(async () => {
    await db.query(`DELETE FROM users WHERE email LIKE '%@integration-test.com'`)
  })
  
  test('creates a user and returns tokens', async () => {
    const response = await request(app)
      .post('/api/v1/auth/register')
      .send({
        email: 'new@integration-test.com',
        password: 'SecurePass123!',
        display_name: 'Test User',
      })
    
    expect(response.status).toBe(201)
    expect(response.body.user.email).toBe('new@integration-test.com')
    expect(response.body.access_token).toBeTruthy()
    
    // Verify the user exists in DB
    const user = await db.query(`SELECT * FROM users WHERE email = 'new@integration-test.com'`)
    expect(user.rows.length).toBe(1)
    expect(user.rows[0].password_hash).not.toBe('SecurePass123!')  // hashed
  })
  
  test('rejects duplicate email', async () => {
    await request(app).post('/api/v1/auth/register').send({
      email: 'dup@integration-test.com', password: 'SecurePass123!'
    })
    
    const response = await request(app).post('/api/v1/auth/register').send({
      email: 'dup@integration-test.com', password: 'SecurePass123!'
    })
    
    expect(response.status).toBe(409)
    expect(response.body.error.code).toBe('EMAIL_EXISTS')
  })
})
```

## Why You Don't Mock Stripe

The most common testing mistake with Stripe: mocking the Stripe SDK.

When you mock `stripe.paymentIntents.create()` to return a fake PaymentIntent, your test passes. But you're testing that your code calls the mocked function, not that Stripe actually works. When your real Stripe integration has a bug — wrong parameter, API version change, missing field — the mock hides it.

**Instead:**
- Use Stripe's **test mode** (default when you use `sk_test_` keys)
- Use **Stripe test card numbers** (4242 4242 4242 4242 always succeeds)
- Use the **Stripe CLI** to trigger webhooks locally
- In CI: use your `sk_test_` key (safe — no real charges in test mode)

The Stripe test environment is the right integration partner. Mocks are not.

## What NOT to Test

- **Framework internals**: Express routing, Stripe SDK internals
- **Third-party library behavior**: bcrypt correctness, JWT library parsing
- **Infrastructure**: That PostgreSQL stores data correctly
- **Obvious things**: That `2 + 2 === 4` in a utility file

Testing these adds maintenance burden without finding bugs in YOUR code.

The bar: does this test catch a bug that could happen in this specific codebase? If yes, write it. If it's testing something another project or library is responsible for, skip it.
