# Lesson 7.1 — What Multi-Tenancy Is

## The Problem Multi-Tenancy Solves

You've built a SaaS platform. Your first customer is Company A. They love it. Company B wants to use it too.

Option 1: Deploy a separate copy of the app for each company. They each get their own database, their own server, their own URL. This is called **single-tenant** or **siloed** architecture.

Option 2: One copy of the app, one database, one server — but each company's data is completely isolated from every other company's data. This is **multi-tenancy**.

Option 2 is what almost every SaaS company uses. It's more economical (one server vs many) and easier to maintain (one codebase to deploy). The challenge: getting the isolation right.

---

## What "Isolation" Means

Isolation means: Company A's users cannot see, access, or modify Company B's data. Not even accidentally. Not even with a bug in your code.

The most dangerous bug in multi-tenant systems is a missing filter. Imagine:
```sql
-- Single-tenant: works fine
SELECT * FROM subscriptions WHERE user_id = $1

-- Multi-tenant: DANGER — if organization_id filter is missing,
-- user from Org A can see Org B's subscriptions
SELECT * FROM subscriptions WHERE user_id = $1
-- Missing: AND organization_id = $2
```

One forgotten `AND organization_id = ?` and you have a data breach.

---

## The Three Approaches

### Approach 1: Separate databases per tenant

Each company gets their own database. True isolation — impossible to mix data.

**Pros:** Maximum isolation, one tenant's heavy load can't affect others, easy to delete a tenant's data
**Cons:** N databases to manage, migrations must run N times, expensive for small tenants

When to use: Enterprise contracts where tenants explicitly require data isolation (regulatory, security audits)

### Approach 2: Separate schemas per tenant

One database, but each tenant gets their own set of tables (in PostgreSQL: a schema, which is a namespace for tables).

**Pros:** Still strong isolation, easier than separate databases
**Cons:** Complex connection management, still need to manage N schemas

When to use: Regulated industries (healthcare, finance) where schema-level isolation satisfies requirements

### Approach 3: Shared database with tenant column (what we use)

One database, all tenants share the same tables. Every row that belongs to a tenant has an `organization_id` column. All queries filter by `organization_id`.

**Pros:** Simple to implement, one migration affects all tenants, most efficient use of resources
**Cons:** Isolation is enforced by application code and indexes, not by the database structure — requires discipline

When to use: Almost all SaaS products start here. This is the approach used by GitHub, Shopify, Slack, and most modern SaaS.

## Which Tables Are Org-Scoped?

| Table | Org-scoped? | Why |
|-------|------------|-----|
| `users` | Yes | Users belong to orgs |
| `subscriptions` | Yes | Each org has its own subscriptions |
| `invoices` | Yes | Per-org billing |
| `payments` | Yes | Per-org payments |
| `products` | Maybe | If products are per-org; for our platform, they're global |
| `plans` | No | Plans are global (defined by the platform, not per org) |
| `prices` | No | Platform-wide pricing |
| `coupons` | Maybe | If coupons can be org-specific |
| `roles` | No | Roles are platform-global |
| `permissions` | No | Permissions are platform-global |
| `organization_members` | Yes | Junction table |
| `webhook_events` | No | Platform-global Stripe events |
| `audit_logs` | Yes | Audit logs are per-org |

**For our course project:** Products are platform-level (all orgs see the same products). Each org has its own subscriptions and billing.

## The Tenant Header Pattern

How does your server know which organization the request belongs to?

Options:
1. **Subdomain:** `company-a.yourapp.com` vs `company-b.yourapp.com`
2. **Custom header:** `X-Organization-Id: org_abc123`
3. **JWT claim:** Include `organization_id` in the JWT payload
4. **URL path:** `/api/v1/org/abc123/subscriptions`

For our course project: include `organization_id` in the JWT. When a user logs in, their primary `organization_id` is included in the token.

For multi-org users (a user belonging to multiple orgs), use a header to specify the current org context.
