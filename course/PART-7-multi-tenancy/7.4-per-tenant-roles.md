# Lesson 7.4 — Per-Tenant Roles and Permissions

## The Role Scope Problem

Before multi-tenancy, a user has a role like `admin` or `member`. With multi-tenancy, the role must be scoped to the organization:

- Alice is `admin` of **Org A** — she can manage Org A's users and settings
- Alice is `member` of **Org B** — she can only view and subscribe
- Alice has no access to **Org C** at all

This is fundamentally different from a flat role. "Alice is admin" means nothing in a multi-tenant system. "Alice is admin OF Org A" does.

---

## The `organization_members` Table

This table stores the role per user per organization:

```sql
organization_members:
  id              UUID
  organization_id UUID → organizations
  user_id         UUID → users
  role_id         UUID → roles   ← role WITHIN this org
  invited_by      UUID → users   ← who invited this user
  joined_at       TIMESTAMPTZ
  UNIQUE (organization_id, user_id)
```

When Alice logs in and selects Org A as her current context, her role from `organization_members` is used for all authorization decisions — not any global role.

## The JWT With Org Context

Update the JWT payload to include org context:

```javascript
export function generateAccessToken(userId, orgId, roleInOrg) {
  return jwt.sign(
    {
      user_id: userId,
      organization_id: orgId,
      role: roleInOrg,       // role within the specified org
    },
    config.auth.accessSecret,
    { expiresIn: config.auth.accessExpiresIn }
  )
}
```

At login, look up the user's role in their primary org:

```javascript
const membership = await db.query(`
  SELECT om.role_id, r.name as role_name
  FROM organization_members om
  JOIN roles r ON r.id = om.role_id
  WHERE om.user_id = $1 AND om.organization_id = $2
`, [user.id, user.organization_id])

const roleInOrg = membership.rows[0]?.role_name ?? 'member'

const accessToken = generateAccessToken(user.id, user.organization_id, roleInOrg)
```

## Inviting Users to an Organization

```javascript
// handlers/organizations.js

export async function inviteUser(req, res) {
  const { email, role = 'member' } = req.body
  const orgId = req.organizationId
  const inviter = req.user
  
  // Can only invite to roles at or below your own
  const allowedRoles = getAllowedInviteRoles(inviter.role)
  if (!allowedRoles.includes(role)) {
    return res.status(403).json({
      error: { code: 'CANNOT_ASSIGN_ROLE', message: `You cannot assign the ${role} role.` }
    })
  }
  
  // Find or create user
  let user = await db.query(`SELECT id FROM users WHERE email = $1`, [email.toLowerCase()])
  
  if (!user.rows.length) {
    // User doesn't exist — create a pending account and send invite email
    // (invite flow details are out of scope for this lesson)
  }
  
  const userId = user.rows[0].id
  
  // Add to org
  const roleRecord = await db.query(`SELECT id FROM roles WHERE name = $1`, [role])
  
  await db.query(`
    INSERT INTO organization_members (id, organization_id, user_id, role_id, invited_by)
    VALUES (uuid_generate_v4(), $1, $2, $3, $4)
    ON CONFLICT (organization_id, user_id)
    DO UPDATE SET role_id = $3
  `, [orgId, userId, roleRecord.rows[0].id, inviter.id])
  
  return res.json({ message: `User invited as ${role}.` })
}

function getAllowedInviteRoles(inviterRole) {
  // Admins can invite admins and members
  // Members can't invite anyone
  const hierarchy = {
    admin: ['admin', 'member', 'support'],
    support: [],
    member: [],
  }
  return hierarchy[inviterRole] ?? []
}
```

## Super-Admin Role (Platform-Level)

A "super-admin" is a platform-level role — not an org role. This user works at the company that built the SaaS and has access across all orgs.

Store this as a flag or a special role in the `users` table, separate from org membership:

```sql
-- Option A: Flag on users table
ALTER TABLE users ADD COLUMN is_platform_admin BOOLEAN NOT NULL DEFAULT false;

-- Option B: Special role in user_roles (no org scope)
-- Use user_roles for platform-level roles
-- Use organization_members for org-scoped roles
```

Check in middleware:
```javascript
// In authenticate middleware
req.user = {
  id: user.id,
  email: user.email,
  role: payload.role,                    // org-scoped role from JWT
  organization_id: payload.organization_id,
  is_platform_admin: user.is_platform_admin,  // from DB
}
```

Platform admin endpoints check `req.user.is_platform_admin`:
```javascript
router.get('/platform/all-organizations',
  authenticate,
  (req, res, next) => {
    if (!req.user.is_platform_admin) {
      return res.status(403).json({ error: { code: 'FORBIDDEN', message: 'Platform admin required.' } })
    }
    next()
  },
  listAllOrganizations
)
```

## Summary of the Multi-Tenancy Additions

| Addition | Purpose |
|----------|---------|
| `organization_id` on user-data tables | Scopes data to a tenant |
| `organization_members` table | Per-user, per-org role assignment |
| `resolveOrganization` middleware | Attaches org context to every request |
| Repository pattern | Guarantees `organization_id` filter on all queries |
| Org-scoped JWT | Role in token reflects role in current org |
| Super-admin flag | Platform-level access across all tenants |
| Tenant isolation tests | Regression tests for the most critical security property |

After Part 7, the system is multi-tenant. Part 8 covers the final production-readiness concerns.
