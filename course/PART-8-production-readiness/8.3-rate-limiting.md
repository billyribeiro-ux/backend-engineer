# Lesson 8.3 — Rate Limiting

## What Rate Limiting Protects Against

**Brute-force attacks:** An attacker tries 10,000 passwords against the same account. Without rate limiting: they could succeed in hours. With rate limiting (5 attempts / 15 min): they'd need months.

**Credential stuffing:** An attacker uses a list of username/password pairs from a data breach to try every combination. Rate limiting slows this to impractical speeds.

**API abuse:** A badly written client (or malicious actor) hammers your API with thousands of requests per second, degrading service for everyone.

---

## Rate Limiting Strategies

### Per-IP rate limiting
Limit based on the client's IP address. Good for unauthenticated endpoints (login, register).

Weakness: Attackers can use many different IPs (distributed attacks). Easy to accidentally block a shared IP (office NAT, VPN).

### Per-user rate limiting
Limit based on the authenticated user ID. Good for authenticated API endpoints.

Strength: Accurately targets individual users. A shared IP doesn't cause collateral damage.

### Per-endpoint rate limiting
Different limits for different endpoints. Login gets stricter limits than a data API.

---

## Implementation with Redis

Rate limiting requires a counter that persists across requests and resets after a time window. Redis is the standard tool for this.

```bash
npm install ioredis rate-limiter-flexible
```

```javascript
// middleware/rateLimiter.js
import { RateLimiterRedis } from 'rate-limiter-flexible'
import Redis from 'ioredis'
import { config } from '../config.js'

const redis = new Redis(config.redis.url)

// Login rate limiter: 5 attempts per 15 minutes per IP
export const loginLimiter = new RateLimiterRedis({
  storeClient: redis,
  keyPrefix: 'login',
  points: config.rateLimit.loginMax,        // 5 attempts
  duration: config.rateLimit.loginWindowMinutes * 60,  // 15 min in seconds
})

// API rate limiter: 100 requests per minute per user
export const apiLimiter = new RateLimiterRedis({
  storeClient: redis,
  keyPrefix: 'api',
  points: config.rateLimit.apiMax,          // 100 requests
  duration: config.rateLimit.apiWindowMinutes * 60,    // 1 min in seconds
})

// Middleware factory
export function rateLimit(limiter, keyFn) {
  return async (req, res, next) => {
    const key = keyFn(req)
    
    try {
      await limiter.consume(key)
      next()
    } catch (rateLimiterRes) {
      const retryAfter = Math.ceil(rateLimiterRes.msBeforeNext / 1000)
      
      res.set('Retry-After', String(retryAfter))
      res.set('X-RateLimit-Limit', String(limiter.points))
      res.set('X-RateLimit-Remaining', String(rateLimiterRes.remainingPoints))
      res.set('X-RateLimit-Reset', String(Date.now() + rateLimiterRes.msBeforeNext))
      
      return res.status(429).json({
        error: {
          code: 'RATE_LIMIT_EXCEEDED',
          message: `Too many requests. Please try again in ${retryAfter} seconds.`,
          retry_after_seconds: retryAfter,
        }
      })
    }
  }
}
```

Apply to routes:
```javascript
// routes/auth.js
import { rateLimit, loginLimiter, apiLimiter } from '../middleware/rateLimiter.js'

// Login: rate limit by IP
router.post('/auth/login',
  rateLimit(loginLimiter, req => req.ip),
  login
)

// Register: rate limit by IP (prevent mass account creation)
router.post('/auth/register',
  rateLimit(loginLimiter, req => req.ip),
  register
)

// General API: rate limit by user ID (after authentication)
const apiRateLimit = rateLimit(apiLimiter, req => req.user?.id ?? req.ip)

// Apply to all authenticated routes
router.use(authenticate)
router.use(apiRateLimit)
```

---

## The Headers You Must Set

When rate limiting, always return these headers (clients use them to know when to retry):

```
Retry-After: 45           -- seconds until limit resets
X-RateLimit-Limit: 5      -- max requests allowed in window
X-RateLimit-Remaining: 0  -- requests remaining in current window
X-RateLimit-Reset: 1716900000  -- Unix timestamp when window resets
```

These are standard headers that HTTP clients understand. A well-behaved client will automatically wait and retry.

## Rate Limit Config in `.env.example`

```bash
# Login rate limiting
RATE_LIMIT_LOGIN_MAX=5
RATE_LIMIT_LOGIN_WINDOW_MINUTES=15

# General API rate limiting (per authenticated user)
RATE_LIMIT_API_MAX=100
RATE_LIMIT_API_WINDOW_MINUTES=1
```

This makes limits configurable without code changes. In production, you might tighten or loosen these based on observed traffic patterns.

---

## What to Rate Limit (Priority Order)

1. **Login endpoint** — highest priority, brute force target
2. **Register endpoint** — prevent mass account creation
3. **Password reset** — prevent enumeration and abuse
4. **Coupon validation** — prevent code scanning
5. **General API** — prevent abuse by authenticated users
6. **Webhook endpoint** — DO NOT rate limit (Stripe needs to send events reliably)
