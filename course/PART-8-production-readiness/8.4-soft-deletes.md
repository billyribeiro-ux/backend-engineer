# Lesson 8.4 — Soft Deletes and Data Retention

## Why You Almost Never Hard Delete in Billing Systems

**Hard delete:** `DELETE FROM subscriptions WHERE id = 'abc'` — gone forever.

**Soft delete:** `UPDATE subscriptions SET deleted_at = NOW() WHERE id = 'abc'` — hidden but still there.

In a billing system, hard deleting is almost always wrong:

1. **Invoices reference subscriptions.** If you hard-delete the subscription, the invoice's foreign key becomes broken. Historical billing records become corrupted.

2. **Audit logs reference everything.** If you delete a user, the audit log entries for that user's actions become orphaned. You can no longer reconstruct what happened.

3. **Stripe keeps records forever.** Your database said the subscription never existed, but Stripe's database has the full history. Now your data is inconsistent with Stripe.

4. **Legal disputes.** A customer claims they canceled but were still charged. You hard-deleted the subscription. You have no evidence. You lose.

---

## The Soft Delete Pattern

Every user-facing entity has `deleted_at TIMESTAMPTZ` (from the schema in Lesson 1.2). This column is:
- `NULL` when the row is active
- A timestamp when the row is soft-deleted

All queries filter `WHERE deleted_at IS NULL` to exclude soft-deleted records:

```sql
-- Active products only
SELECT * FROM products WHERE deleted_at IS NULL AND is_active = true

-- Active subscriptions for a user
SELECT * FROM subscriptions WHERE user_id = $1 AND deleted_at IS NULL
```

## The Repository Pattern With Soft Deletes

```javascript
// In the repository, soft delete is always the default
class UserRepository {
  async delete(userId, actorId) {
    await db.transaction(async (client) => {
      // Soft delete the user
      await client.query(`
        UPDATE users SET deleted_at = NOW(), updated_at = NOW() WHERE id = $1
      `, [userId])
      
      // Audit log
      await client.query(`
        INSERT INTO audit_logs (id, actor_id, action, resource_type, resource_id, created_at)
        VALUES (uuid_generate_v4(), $1, 'user.deleted', 'user', $2, NOW())
      `, [actorId, userId])
    })
  }
  
  async findById(id) {
    const result = await db.query(`
      SELECT * FROM users WHERE id = $1 AND deleted_at IS NULL
    `, [id])
    return result.rows[0] ?? null
  }
  
  // For admin queries that need to see deleted records
  async findByIdIncludingDeleted(id) {
    const result = await db.query(`SELECT * FROM users WHERE id = $1`, [id])
    return result.rows[0] ?? null
  }
}
```

## GDPR: When You Must Delete (And How)

GDPR gives users the "right to erasure" — the right to have their personal data deleted. But in billing systems, you can't delete payment records (those have their own legal retention requirements — typically 7 years).

The solution: **anonymize, don't delete.**

```javascript
export async function gdprDeleteUser(userId) {
  await db.transaction(async (client) => {
    // Anonymize the user — remove PII but keep the record
    await client.query(`
      UPDATE users SET
        email = $1,           -- anonymized email
        password_hash = '',   -- clear password
        display_name = 'Deleted User',
        stripe_customer_id = NULL,  -- unlink from Stripe
        deleted_at = NOW(),
        updated_at = NOW()
      WHERE id = $2
    `, [`deleted_${userId}@anonymized.invalid`, userId])
    
    // Cancel any active subscriptions in Stripe
    const subscriptions = await client.query(`
      SELECT stripe_subscription_id FROM subscriptions
      WHERE user_id = $1 AND status IN ('active', 'trialing', 'past_due')
    `, [userId])
    
    for (const sub of subscriptions.rows) {
      await stripe.subscriptions.cancel(sub.stripe_subscription_id)
    }
    
    // The invoices and payments stay — they're financial records
    // But we remove the user's PII from our system
    
    // Delete the Stripe customer (removes payment methods from Stripe's side)
    const user = await client.query(`SELECT stripe_customer_id FROM users WHERE id = $1`, [userId])
    if (user.rows[0]?.stripe_customer_id) {
      await stripe.customers.del(user.rows[0].stripe_customer_id)
    }
    
    // Audit log the deletion
    await client.query(`
      INSERT INTO audit_logs (id, actor_id, action, resource_type, resource_id, metadata, created_at)
      VALUES (uuid_generate_v4(), $1, 'user.gdpr_deleted', 'user', $1, '{"gdpr": true}', NOW())
    `, [userId])
  })
}
```

The record stays. The personal data is gone. The billing history remains for legal compliance.

## Indexes for Soft Deletes

All indexes on soft-deleted tables should include the `WHERE deleted_at IS NULL` condition for performance:

```sql
CREATE INDEX idx_users_email ON users(email) WHERE deleted_at IS NULL;
CREATE INDEX idx_subscriptions_user ON subscriptions(user_id) WHERE deleted_at IS NULL;
CREATE INDEX idx_products_active ON products(is_active) WHERE deleted_at IS NULL;
```

These **partial indexes** are smaller (only cover active rows) and faster than full-table indexes.
