# Lesson 8.5 — Database Migrations

## What a Migration Is

A migration is a versioned, repeatable script that changes the database schema. Each migration is:
- **Numbered** (run in order)
- **Tracked** (the database knows which migrations have been applied)
- **Forward-only** in production (you don't roll back migrations — you write new ones)

---

## The Migration Table

A `migrations` table tracks which migrations have been applied:

```sql
CREATE TABLE migrations (
  id        SERIAL PRIMARY KEY,
  name      TEXT NOT NULL UNIQUE,
  run_at    TIMESTAMPTZ NOT NULL DEFAULT NOW()
)
```

When the migration runner starts, it checks which migration files exist, compares to the `migrations` table, and runs only the ones not yet applied.

---

## Migration File Naming

```
migrations/
  001_initial_schema.sql
  002_add_multi_tenancy.sql
  003_add_user_product_access.sql
  004_add_platform_admin_flag.sql
```

The numeric prefix guarantees order. The descriptive name tells you what the migration does without opening the file.

## The Migration Runner

```javascript
// db/migrate.js
import fs from 'fs'
import path from 'path'
import { fileURLToPath } from 'url'
import db from './index.js'

const __dirname = path.dirname(fileURLToPath(import.meta.url))
const MIGRATIONS_DIR = path.join(__dirname, '..', 'migrations')

async function migrate() {
  // Ensure migrations table exists
  await db.query(`
    CREATE TABLE IF NOT EXISTS migrations (
      id     SERIAL PRIMARY KEY,
      name   TEXT NOT NULL UNIQUE,
      run_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
    )
  `)
  
  // Get applied migrations
  const applied = await db.query('SELECT name FROM migrations ORDER BY id')
  const appliedNames = new Set(applied.rows.map(r => r.name))
  
  // Get all migration files, sorted by name (numeric order)
  const files = fs.readdirSync(MIGRATIONS_DIR)
    .filter(f => f.endsWith('.sql'))
    .sort()
  
  let ran = 0
  
  for (const file of files) {
    if (appliedNames.has(file)) continue  // Already applied
    
    console.log(`Running migration: ${file}`)
    const sql = fs.readFileSync(path.join(MIGRATIONS_DIR, file), 'utf-8')
    
    await db.transaction(async (client) => {
      await client.query(sql)
      await client.query('INSERT INTO migrations (name) VALUES ($1)', [file])
    })
    
    console.log(`✓ ${file} applied`)
    ran++
  }
  
  if (ran === 0) {
    console.log('No pending migrations.')
  } else {
    console.log(`\n✓ ${ran} migration(s) applied.`)
  }
}

migrate()
  .then(() => process.exit(0))
  .catch(err => {
    console.error('Migration failed:', err)
    process.exit(1)
  })
```

```json
// package.json scripts
{
  "scripts": {
    "db:migrate": "node src/db/migrate.js",
    "db:seed": "node src/db/seed.js",
    "db:setup": "npm run db:migrate && npm run db:seed"
  }
}
```

## Safe vs Unsafe Migrations

### Safe (can run without downtime):
- Adding a new table
- Adding a nullable column
- Adding an index (though this can lock for large tables — use `CREATE INDEX CONCURRENTLY`)
- Adding a CHECK constraint (if existing data satisfies it)

### Requires care:
- Adding a NOT NULL column to an existing table → must backfill first, then add constraint
- Renaming a column → do this in 3 steps: add new column, copy data, remove old column
- Removing a column → ensure all code stops using it before removing

### Never do in production:
- `DROP TABLE` while the application is using it
- `ALTER TABLE ... ALTER COLUMN type` on a column with existing data (may require a cast)
- Changing a constraint in a way that existing data violates

---

## The 3-Step Pattern for Breaking Changes

When you need to rename a column or change a type:

**Step 1 (deploy 1):** Add new column, write to both old and new columns:
```sql
ALTER TABLE users ADD COLUMN full_name TEXT;
```
Update application code to write to both `display_name` and `full_name`.

**Step 2 (deploy 2):** Backfill new column, read from new column:
```sql
UPDATE users SET full_name = display_name WHERE full_name IS NULL;
```
Update application code to read from `full_name`.

**Step 3 (deploy 3):** Remove old column:
```sql
ALTER TABLE users DROP COLUMN display_name;
```

Three deployments. Zero downtime. Zero data loss.
