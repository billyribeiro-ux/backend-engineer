## The Pre-Production Checklist

Before flipping to production keys, verify every item:

### Environment Variables
- [ ] `NODE_ENV=production` is set
- [ ] `STRIPE_SECRET_KEY` starts with `sk_live_` (not `sk_test_`)
- [ ] `STRIPE_PUBLISHABLE_KEY` starts with `pk_live_`
- [ ] `STRIPE_WEBHOOK_SECRET` is the live mode webhook secret (create a new endpoint in Stripe Dashboard → Webhooks)
- [ ] `JWT_ACCESS_SECRET` and `JWT_REFRESH_SECRET` are cryptographically random (at least 64 chars)
- [ ] `DATABASE_URL` points to the production database (not localhost)
- [ ] `REDIS_URL` points to a production Redis instance
- [ ] `CORS_ORIGINS` contains only your production frontend domain
- [ ] `BCRYPT_ROUNDS` is 12 or higher
- [ ] `LOG_LEVEL=warn` or `error` in production (reduce log volume)
- [ ] `SENTRY_DSN` is set (error tracking active)

### Database
- [ ] All migrations have been run (`npm run db:migrate`)
- [ ] Required seeds have been run (`NODE_ENV=production npm run db:seed`)
- [ ] Test seeds have NOT been run (the guard in seed files prevents this)
- [ ] Database has connection pooling configured appropriately
- [ ] Indexes are in place (run `EXPLAIN ANALYZE` on your most common queries)

### Stripe
- [ ] Products and plans are synced to Stripe live mode
- [ ] Prices are synced to Stripe live mode
- [ ] Webhook endpoint registered in Stripe Dashboard → Webhooks with your production URL
- [ ] Webhook events subscribed: `payment_intent.succeeded`, `payment_intent.payment_failed`, `invoice.paid`, `invoice.payment_failed`, `customer.subscription.created`, `customer.subscription.updated`, `customer.subscription.deleted`, `customer.subscription.trial_will_end`

### Security
- [ ] HTTPS is enforced (not HTTP)
- [ ] Cookies use `secure: true` and `sameSite: 'strict'`
- [ ] Rate limiting is active on login, register, and API endpoints
- [ ] Error responses don't expose internal details
- [ ] All endpoints that should be protected have `authenticate` middleware

### Functionality
- [ ] Login, register, refresh token flow works
- [ ] Product purchase flow works end-to-end (Stripe test → Stripe live)
- [ ] Subscription creation works
- [ ] Webhooks are received and processed
- [ ] Coupon validation and application works
- [ ] Subscription cancellation works

### Health
- [ ] Health check endpoint exists: `GET /health` → `{ status: 'ok', timestamp: '...' }`
- [ ] Database connection check included in health response
- [ ] Monitoring/alerting is configured (uptime, error rate, response time)

## The Health Check Endpoint

```javascript
router.get('/health', async (req, res) => {
  try {
    // Check database connection
    await db.query('SELECT 1')
    
    return res.json({
      status: 'ok',
      timestamp: new Date().toISOString(),
      version: process.env.npm_package_version,
      services: {
        database: 'ok',
      }
    })
  } catch (err) {
    return res.status(503).json({
      status: 'error',
      timestamp: new Date().toISOString(),
      services: {
        database: 'error',
      }
    })
  }
})
```

This endpoint is hit by your load balancer or monitoring service every 30 seconds. If it returns non-200, traffic is routed away from the failing instance.

## What's Left to Actually Deploy

This course gets you to "deploy-ready." The actual deployment requires:

1. **Docker** — containerize your app (separate topic)
2. **Hosting** — Railway, Render, Fly.io, AWS, or any VPS
3. **Managed PostgreSQL** — Supabase, Neon, RDS, or any hosted Postgres
4. **Managed Redis** — Upstash, Redis Cloud, or ElastiCache
5. **Stripe production webhook endpoint** — register your production URL in Stripe Dashboard
6. **DNS** — point your domain to your server

None of these require changing application code. They're infrastructure decisions. The code is ready.
