# Lesson 9.1 — Why Rust for Production Backend

## The Mental Model Transfers

Everything you built in Node.js — the database schema, the API contract, the RBAC/ABAC policies, the Stripe webhook logic, the grandfathering logic — none of that changes. The mental model is the same.

What changes: the language that implements it.

This is the payoff of designing before coding. Good design is language-agnostic. An engineer who understands the system can implement it in any language. Part 9 proves this.

---

## Why Rust?

**Memory safety without garbage collection.**

In languages like Node.js, Python, or Go, a garbage collector (GC) manages memory — it periodically frees memory that's no longer needed. This is convenient but introduces GC pauses: brief moments where the program stops to collect garbage.

Rust achieves memory safety without a GC. The compiler analyzes ownership and lifetimes at compile time and generates code that frees memory exactly when it's no longer needed. Zero pauses. Predictable latency.

**Performance characteristics:**
- Rust backend latency is typically comparable to C/C++ — microseconds, not milliseconds
- Node.js is single-threaded by default (worker threads exist but are cumbersome)
- Rust uses true OS threads with Tokio providing async I/O — handles concurrent requests efficiently

**The compiler as a safety net:**
- The Rust compiler catches null pointer dereferences at compile time (they can't occur at runtime)
- Type mismatches, use-after-free, data races — all caught before the program runs
- This means Rust programs that compile tend to work correctly

**When Rust is the right choice:**
- High-throughput APIs (thousands of requests per second)
- Latency-sensitive services
- Systems where reliability matters more than development speed
- When you need to run in resource-constrained environments

**When Rust is overkill:**
- Prototypes and MVPs
- Low-traffic internal tools
- When developer velocity is more important than performance

For our course project: a production billing system that needs to be reliable and handle real traffic. Rust is appropriate.

## The Axum + Tokio + SQLx Stack

**Tokio** — the async runtime. Rust is synchronous by default. Tokio adds `async/await` support and an event loop, similar to Node.js's event loop but capable of using all CPU cores.

**Axum** — the web framework. Built on top of Tokio. Clean, composable middleware (called "layers" in Axum), first-class support for type-safe extractors.

**SQLx** — the database library. Queries are verified against your actual database schema at compile time. If you reference a column that doesn't exist, the code won't compile. This catches SQL typos before they reach production.

**The stack analogy:**
- Tokio ≈ Node.js event loop
- Axum ≈ Express/Fastify
- SQLx ≈ node-postgres + compile-time verification
