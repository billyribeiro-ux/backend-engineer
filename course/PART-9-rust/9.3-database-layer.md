# Lesson 9.3 — The Database Layer in Rust

## What's Different From Node.js

In Node.js, SQL errors are runtime errors. You typo a column name, the query runs, it fails, your server crashes or returns a 500. You only find out in production — or if you have good tests.

In Rust with SQLx, **SQL errors are compile-time errors**. You typo a column name, `cargo build` fails and tells you exactly which line is wrong. The compiler actually connects to your database during compilation and verifies every query against the real schema.

This is the single biggest practical advantage of SQLx over every Node.js database library.

---

## How SQLx Works

```
cargo build
  → sqlx reads every sqlx::query! macro in your code
  → connects to the database at DATABASE_URL
  → runs EXPLAIN on every query to verify it
  → checks that column names exist, types match, bind params are correct
  → if anything is wrong: compile error
```

If the database isn't available (CI, production build), SQLx falls back to a cached query file (`.sqlx/` directory). You generate this cache with `cargo sqlx prepare` and commit it to git.

---

## Migrations

Migrations in SQLx work the same way as in any migration system — versioned SQL files that run in order. The difference is they run automatically from your Rust code.

**Migration directory:**
```
migrations/
└── 001_initial_schema.sql
```

**Running migrations from code:**
```rust
// in main.rs
sqlx::migrate!("./migrations").run(&db_pool).await?;
```

This runs all pending migrations when the server starts. It's idempotent — already-applied migrations are skipped. SQLx tracks applied migrations in a `_sqlx_migrations` table it creates automatically.

**Running migrations manually:**
```bash
sqlx migrate run
```

## How Queries Work

### The `sqlx::query!` Macro

```rust
// This is verified at compile time
let user = sqlx::query!(
    "SELECT id, email, created_at FROM users WHERE id = $1",
    user_id
)
.fetch_one(&pool)
.await?;

// Accessing fields — these are typed based on your schema
println!("{}", user.email);   // String
println!("{}", user.id);      // Uuid
```

The macro returns an anonymous struct with exactly the columns you selected. The types are inferred from PostgreSQL's type system:
- `UUID` → `uuid::Uuid`
- `TEXT` or `VARCHAR` → `String`
- `TIMESTAMPTZ` → `chrono::DateTime<chrono::Utc>`
- `BOOLEAN` → `bool`
- `INTEGER` → `i32`
- `BIGINT` → `i64`
- `NUMERIC` → `bigdecimal::BigDecimal` or `rust_decimal::Decimal`
- `JSONB` → `serde_json::Value`
- Nullable column → wrapped in `Option<T>`

### The `sqlx::query_as!` Macro

When you want to map query results directly into your own struct:

```rust
// Your model
pub struct User {
    pub id: Uuid,
    pub email: String,
    pub display_name: String,
    pub role: String,
    pub created_at: DateTime<Utc>,
}

// Query into that struct
let user = sqlx::query_as!(
    User,
    "SELECT id, email, display_name, role, created_at FROM users WHERE id = $1",
    user_id
)
.fetch_one(&pool)
.await?;
```

The field names in your struct must match the column names returned by the query. If they don't match, you get a compile error.

## The Four Fetch Methods

```rust
// Returns exactly one row — errors if 0 or 2+ rows
.fetch_one(&pool).await?

// Returns Some(row) or None — errors if 2+ rows
.fetch_optional(&pool).await?

// Returns a Vec<Row> — errors if query fails, not if empty
.fetch_all(&pool).await?

// For INSERT/UPDATE/DELETE — returns rows affected, last insert id
.execute(&pool).await?
```

Choosing the right one matters:
- Use `fetch_one` when the row MUST exist (e.g., fetching after inserting)
- Use `fetch_optional` when the row MIGHT not exist (e.g., find by email)
- Use `fetch_all` for lists
- Use `execute` for writes

## Transactions

When multiple writes must succeed or fail together:

```rust
use sqlx::Acquire;

let mut tx = pool.begin().await?;

// All queries using &mut tx instead of &pool
sqlx::query!(
    "INSERT INTO users (id, email) VALUES ($1, $2)",
    user_id, email
)
.execute(&mut *tx)
.await?;

sqlx::query!(
    "INSERT INTO profiles (user_id, display_name) VALUES ($1, $2)",
    user_id, display_name
)
.execute(&mut *tx)
.await?;

// Commit only if everything succeeded
tx.commit().await?;
// If any .await? above returned Err, the transaction is automatically rolled back
// when `tx` is dropped (Rust's Drop trait handles cleanup)
```

This is the correct pattern for registration: create user + create Stripe customer + insert subscription trial — all in one transaction or none of it.

## Connection Pool

The pool is initialized once at startup and shared across all requests via `AppState`:

```rust
// in main.rs
let db_pool = PgPool::connect(&config.database_url)
    .await
    .context("Failed to connect to PostgreSQL")?;
```

`PgPool` is cloneable and thread-safe. Cloning a pool doesn't create a new connection — it just copies the reference to the shared pool. Axum's `State<AppState>` gives every handler its own clone of `AppState`, which contains the shared pool.

Default pool size is 10 connections. For production:

```rust
let db_pool = PgPoolOptions::new()
    .max_connections(20)
    .acquire_timeout(Duration::from_secs(5))
    .connect(&config.database_url)
    .await?;
```

## The Query Cache (`.sqlx/`)

When you run `cargo sqlx prepare`, SQLx writes a cache of all verified queries to `.sqlx/`. This allows `cargo build` to work offline (in CI, Docker builds) without needing a live database.

```bash
# Generate the cache — run this before committing
cargo sqlx prepare

# Verify the cache is still valid against the current schema
cargo sqlx prepare --check
```

**Add `.sqlx/` to git.** This is intentional. It's the evidence that all your queries were verified against the schema at the time of the commit.

**Add this to your CI pipeline:**
```yaml
- name: Verify SQLx queries
  run: cargo sqlx prepare --check
  env:
    DATABASE_URL: postgres://postgres:password@localhost:5432/saas_test
```

If a developer changes the schema without updating a query, CI fails. If they update a query without running `cargo sqlx prepare`, CI fails. This keeps the query cache in sync.

## Why There Are No Repository Structs in This Project

Many Rust projects wrap all DB queries in a repository struct:

```rust
pub struct UserRepository {
    pool: PgPool,
}

impl UserRepository {
    pub async fn find_by_email(&self, email: &str) -> Result<Option<User>, AppError> {
        // query here
    }
}
```

This is a valid pattern — it centralizes queries, makes them testable in isolation, and keeps handlers thin.

For this course, queries live directly in route handlers. Why:

1. The handlers in this project are small enough that a separate layer adds indirection without adding value
2. SQLx's compile-time verification already catches mistakes — you don't need a repository layer for that
3. Adding repositories before you've felt the pain of not having them is premature abstraction

In a production system with dozens of handlers, you'd add repositories. For this project, keeping queries inline makes the code easier to read without jumping between files.

## Reading the Migrations

The migration file at `migrations/001_initial_schema.sql` is the same SQL schema from Lesson 1.2, adapted for SQLx:

- Uses `uuid_generate_v4()` — requires the `uuid-ossp` extension
- Uses `NOW()` for defaults
- All foreign keys defined inline
- Partial indexes for soft-delete queries

After the migrations run, SQLx has verified that every `sqlx::query!` in your codebase matches this schema exactly.
