# Lesson 9.4 — Authentication in Rust

## The Three Files

Auth in this project is split across three files:

```
src/auth/
├── jwt.rs       — token generation and verification
├── password.rs  — hashing and verification
└── extractor.rs — Axum integration (how handlers receive the current user)
```

The Node.js version used Express middleware — a function that runs before the handler and attaches `req.user`. Axum does this differently. Instead of middleware, it uses **extractors**: types that know how to pull themselves out of an HTTP request.

## Passwords: `src/auth/password.rs`

```rust
use argon2::{
    password_hash::{rand_core::OsRng, PasswordHash, PasswordHasher, PasswordVerifier, SaltString},
    Argon2,
};

pub fn hash_password(password: &str) -> Result<String, anyhow::Error> {
    let salt = SaltString::generate(&mut OsRng);
    let argon2 = Argon2::default();
    let hash = argon2
        .hash_password(password.as_bytes(), &salt)
        .map_err(|e| anyhow::anyhow!("Failed to hash password: {}", e))?;
    Ok(hash.to_string())
}

pub fn verify_password(password: &str, hash: &str) -> Result<bool, anyhow::Error> {
    let parsed_hash = PasswordHash::new(hash)
        .map_err(|e| anyhow::anyhow!("Invalid password hash: {}", e))?;
    Ok(Argon2::default()
        .verify_password(password.as_bytes(), &parsed_hash)
        .is_ok())
}
```

**Why argon2 instead of bcrypt?**

This was touched in Lesson 2.3 (Node.js), but in Rust the answer is the same with one addition: argon2 won the [Password Hashing Competition](https://www.password-hashing.net/) in 2015. It's resistant to GPU attacks (bcrypt is not), and the `argon2` crate in Rust is well-maintained. Both are fine choices; argon2 is the modern recommendation.

**The salt:** `SaltString::generate(&mut OsRng)` generates a cryptographically random salt using the operating system's random number generator. Each password gets a unique salt. This is automatic — you don't manage salts manually.

**The hash output:** A single string like `$argon2id$v=19$m=19456,t=2,p=1$...`. The algorithm, version, parameters, salt, and hash are all encoded together. When you verify, `PasswordHash::new(hash)` parses all of this out. You never store the salt separately.

## JWTs: `src/auth/jwt.rs`

```rust
use jsonwebtoken::{decode, encode, DecodingKey, EncodingKey, Header, Validation};
use serde::{Deserialize, Serialize};
use uuid::Uuid;

#[derive(Debug, Serialize, Deserialize)]
pub struct AccessTokenClaims {
    pub sub: String,      // user ID
    pub email: String,
    pub role: String,
    pub exp: usize,       // expiry (Unix timestamp)
    pub iat: usize,       // issued at
}

#[derive(Debug, Serialize, Deserialize)]
pub struct RefreshTokenClaims {
    pub sub: String,
    pub exp: usize,
    pub iat: usize,
}

pub fn generate_access_token(
    user_id: Uuid,
    email: &str,
    role: &str,
    secret: &str,
    expires_in_secs: u64,
) -> Result<String, anyhow::Error> {
    let now = std::time::SystemTime::now()
        .duration_since(std::time::UNIX_EPOCH)?
        .as_secs();

    let claims = AccessTokenClaims {
        sub: user_id.to_string(),
        email: email.to_string(),
        role: role.to_string(),
        iat: now as usize,
        exp: (now + expires_in_secs) as usize,
    };

    encode(
        &Header::default(),
        &claims,
        &EncodingKey::from_secret(secret.as_bytes()),
    )
    .map_err(|e| anyhow::anyhow!("Failed to generate access token: {}", e))
}

pub fn verify_access_token(
    token: &str,
    secret: &str,
) -> Result<AccessTokenClaims, anyhow::Error> {
    let token_data = decode::<AccessTokenClaims>(
        token,
        &DecodingKey::from_secret(secret.as_bytes()),
        &Validation::default(),
    )
    .map_err(|e| anyhow::anyhow!("Invalid access token: {}", e))?;

    Ok(token_data.claims)
}
```

The `Validation::default()` configuration:
- Verifies the signature
- Checks expiry (`exp` field)
- Expects HS256 algorithm (the default)

That's all you need. You don't need to manually check expiry — the library does it.

## The Extractor: `src/auth/extractor.rs`

This is the most important piece. Understanding how Axum extractors work unlocks the whole design.

```rust
use axum::{
    async_trait,
    extract::FromRequestParts,
    http::{request::Parts, StatusCode},
    Json,
};
use serde_json::json;
use uuid::Uuid;

use crate::{auth::jwt::verify_access_token, state::AppState};

#[derive(Debug, Clone)]
pub struct AuthUser {
    pub id: Uuid,
    pub email: String,
    pub role: String,
    pub organization_id: Option<Uuid>,
}

#[async_trait]
impl FromRequestParts<AppState> for AuthUser {
    type Rejection = (StatusCode, Json<serde_json::Value>);

    async fn from_request_parts(
        parts: &mut Parts,
        state: &AppState,
    ) -> Result<Self, Self::Rejection> {
        // Extract token from Authorization: Bearer <token>
        let token = parts
            .headers
            .get("authorization")
            .and_then(|v| v.to_str().ok())
            .and_then(|v| v.strip_prefix("Bearer "))
            .ok_or_else(|| {
                (
                    StatusCode::UNAUTHORIZED,
                    Json(json!({ "error": "missing_token", "message": "Authentication required." })),
                )
            })?;

        // Verify the token
        let claims = verify_access_token(token, &state.config.jwt_secret).map_err(|_| {
            (
                StatusCode::UNAUTHORIZED,
                Json(json!({ "error": "invalid_token", "message": "Invalid or expired token." })),
            )
        })?;

        let user_id = Uuid::parse_str(&claims.sub).map_err(|_| {
            (
                StatusCode::UNAUTHORIZED,
                Json(json!({ "error": "invalid_token", "message": "Invalid token subject." })),
            )
        })?;

        // Optional: fetch organization context from DB
        let org_row = sqlx::query!(
            "SELECT organization_id FROM organization_members WHERE user_id = $1 LIMIT 1",
            user_id
        )
        .fetch_optional(&state.db)
        .await
        .ok()
        .flatten();

        Ok(AuthUser {
            id: user_id,
            email: claims.email,
            role: claims.role,
            organization_id: org_row.and_then(|r| r.organization_id),
        })
    }
}
```

### How Handlers Use This

```rust
// This handler REQUIRES authentication.
// If the token is missing or invalid, Axum returns 401 before the handler runs.
pub async fn get_me(
    auth: AuthUser,                // ← extractor declares requirement
    State(state): State<AppState>,
) -> Result<Json<UserResponse>, AppError> {
    let user = sqlx::query!(
        "SELECT id, email, display_name, role FROM users WHERE id = $1",
        auth.id
    )
    .fetch_one(&state.db)
    .await?;

    Ok(Json(UserResponse {
        id: user.id,
        email: user.email,
        display_name: user.display_name,
        role: user.role,
    }))
}
```

The handler signature declares what it needs. If `AuthUser` fails to extract (bad token, missing header), Axum automatically returns the rejection — the handler body never executes. **You can't forget to add auth middleware to a route** if the handler itself declares `auth: AuthUser`.

Compare to Express:
```js
// Easy to forget this line — and your route is unprotected
router.get('/me', authenticate, async (req, res) => {
    // req.user is set by middleware
});
```

In Axum:
```rust
// Impossible to forget — the handler won't compile without AuthUser
// if it tries to use auth.id
async fn get_me(auth: AuthUser, ...) -> ...
```

### Optional Auth: `OptionalAuthUser`

For endpoints where auth is optional (public route, but you want to know if someone is logged in):

```rust
pub struct OptionalAuthUser(pub Option<AuthUser>);

#[async_trait]
impl FromRequestParts<AppState> for OptionalAuthUser {
    type Rejection = std::convert::Infallible; // never fails

    async fn from_request_parts(
        parts: &mut Parts,
        state: &AppState,
    ) -> Result<Self, Self::Rejection> {
        // Try to extract AuthUser, but return None if it fails
        let user = AuthUser::from_request_parts(parts, state).await.ok();
        Ok(OptionalAuthUser(user))
    }
}
```

Used in handlers like:
```rust
async fn list_products(
    optional_auth: OptionalAuthUser,
    State(state): State<AppState>,
) -> Result<Json<Vec<ProductResponse>>, AppError> {
    // Show public products to everyone, premium products only to subscribers
    match optional_auth.0 {
        Some(user) => { /* show more */ }
        None => { /* show less */ }
    }
}
```

## The Login Flow: `src/routes/auth.rs`

```rust
pub async fn login(
    State(state): State<AppState>,
    Json(body): Json<LoginRequest>,
) -> Result<Json<AuthResponse>, AppError> {
    // 1. Find user by email
    let user = sqlx::query!(
        "SELECT id, email, password_hash, role FROM users WHERE email = $1",
        body.email
    )
    .fetch_optional(&state.db)
    .await
    .map_err(AppError::Internal)?;

    // 2. Same error for wrong email or wrong password (prevent user enumeration)
    let user = match user {
        Some(u) => u,
        None => {
            return Err(AppError::bad_request("INVALID_CREDENTIALS", "Invalid email or password."));
        }
    };

    // 3. Verify password
    let valid = verify_password(&body.password, &user.password_hash)
        .map_err(|e| AppError::Internal(anyhow::anyhow!(e)))?;

    if !valid {
        return Err(AppError::bad_request("INVALID_CREDENTIALS", "Invalid email or password."));
    }

    // 4. Generate tokens
    let access_token = generate_access_token(
        user.id,
        &user.email,
        &user.role,
        &state.config.jwt_secret,
        state.config.jwt_access_expiry_secs,
    )
    .map_err(|e| AppError::Internal(anyhow::anyhow!(e)))?;

    let refresh_token = generate_refresh_token(
        user.id,
        &state.config.jwt_refresh_secret,
        state.config.jwt_refresh_expiry_secs,
    )
    .map_err(|e| AppError::Internal(anyhow::anyhow!(e)))?;

    // 5. Store refresh token
    sqlx::query!(
        r#"
        INSERT INTO refresh_tokens (id, user_id, token, expires_at)
        VALUES (uuid_generate_v4(), $1, $2, NOW() + INTERVAL '30 days')
        "#,
        user.id,
        refresh_token,
    )
    .execute(&state.db)
    .await
    .map_err(AppError::Internal)?;

    Ok(Json(AuthResponse {
        access_token,
        refresh_token,
        user: UserResponse {
            id: user.id,
            email: user.email,
            display_name: user.display_name.unwrap_or_default(),
            role: user.role,
        },
    }))
}
```

The same user enumeration prevention from Lesson 2.3 applies here: same error message and same response time whether the email doesn't exist or the password is wrong.

## Error Handling in Auth

The `AppError` enum (in `src/errors.rs`) converts directly to HTTP responses. In auth handlers:

```rust
// If the DB is down → 500 Internal Server Error (message: "An internal error occurred.")
.map_err(AppError::Internal)?

// If credentials are wrong → 400 Bad Request with a safe message
AppError::bad_request("INVALID_CREDENTIALS", "Invalid email or password.")

// If the token is invalid → 401 Unauthorized
// This happens inside the extractor, before the handler runs
```

The caller never sees database errors, stack traces, or internal details. They see the safe message.

## What's the Same as Node.js

- The same JWT claims structure (sub, email, role, exp, iat)
- The same access/refresh token pattern
- The same user enumeration prevention
- The same httpOnly cookie strategy (available — just use `axum-extra` cookie jar)
- The same token rotation on refresh

**What's different:**

- No `req.user` — the user is declared as a parameter, not attached to a request object
- No middleware registration per route — auth is automatic if the handler declares `AuthUser`
- Compile-time guarantees that you're accessing `.id` on a real `AuthUser`, not a potentially-missing `req.user`
- `argon2` instead of `bcrypt` (same concept, better algorithm)
