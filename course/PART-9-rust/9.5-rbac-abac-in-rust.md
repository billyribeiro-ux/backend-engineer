# Lesson 9.5 — RBAC + ABAC in Rust

## How the Rust Implementation Maps to Part 3

In Part 3, you learned:
- **RBAC**: role-based, context-free ("admins can always manage users")
- **ABAC**: attribute-based, contextual ("you can only edit your own profile")
- **Both**: role gate first, then context check ("only admins can delete, and only if the resource isn't locked")

The Rust implementation uses the same logic — it's just expressed differently because of Rust's type system and Axum's extractor model.

The two files that implement this:

```
src/
├── policies/mod.rs      — ABAC: pure functions that return bool
└── middleware/rbac.rs   — RBAC: permission check against the database
```

---

## ABAC: Policy Functions — `src/policies/mod.rs`

Policy functions are pure: they take data in, return `bool` out. No database calls. No side effects.

```rust
use uuid::Uuid;
use crate::auth::extractor::AuthUser;
use crate::models::subscription::Subscription;

/// A member can edit their own profile. An admin can edit anyone's profile.
/// An org owner cannot be edited by another admin (only themselves or platform admin).
pub fn can_edit_profile(user: &AuthUser, target_user_id: Uuid, is_org_owner: bool) -> bool {
    if user.id == target_user_id {
        return true; // always edit your own
    }
    if user.role == "admin" && !is_org_owner {
        return true; // admin can edit non-owners
    }
    false
}

/// A member can view their own subscription.
/// An admin can view any subscription in their organization.
pub fn can_view_subscription(user: &AuthUser, subscription_owner_id: Uuid) -> bool {
    user.id == subscription_owner_id || user.role == "admin"
}

/// A member can cancel their own subscription.
/// Admins cannot cancel other users' subscriptions (billing autonomy).
pub fn can_cancel_subscription(user: &AuthUser, subscription_owner_id: Uuid) -> bool {
    user.id == subscription_owner_id
}

/// Active subscription check for premium content.
pub fn has_active_subscription(subscription: &Subscription) -> bool {
    subscription.has_active_access()
}

/// Only platform-level admins can delete users.
/// Org admins cannot delete users from other orgs.
pub fn can_delete_user(
    actor: &AuthUser,
    target_user_id: Uuid,
    target_org_id: Option<Uuid>,
) -> bool {
    if actor.role != "admin" {
        return false;
    }
    // Org admin can only delete users in their own org
    match (actor.organization_id, target_org_id) {
        (Some(actor_org), Some(target_org)) => actor_org == target_org,
        (None, _) => true, // platform admin — no org restriction
        _ => false,
    }
}
```

### Using Policy Functions in Handlers

```rust
pub async fn update_profile(
    auth: AuthUser,
    Path(user_id): Path<Uuid>,
    State(state): State<AppState>,
    Json(body): Json<UpdateProfileRequest>,
) -> Result<Json<UserResponse>, AppError> {
    // Check if the target user is an org owner
    let target = sqlx::query!(
        "SELECT is_org_owner FROM users WHERE id = $1",
        user_id
    )
    .fetch_optional(&state.db)
    .await
    .map_err(AppError::Internal)?
    .ok_or(AppError::NotFound)?;

    // ABAC check — pure function call
    if !can_edit_profile(&auth, user_id, target.is_org_owner) {
        return Err(AppError::Forbidden);
    }

    // Proceed with the update
    // ...
}
```

The policy function is called with real data. The handler's job is to:
1. Fetch the data the policy needs
2. Call the policy
3. Return 403 if the policy says no
4. Proceed if the policy says yes

## Testing Policy Functions

Because they're pure functions, tests are trivial:

```rust
#[cfg(test)]
mod tests {
    use super::*;
    use uuid::Uuid;
    use crate::auth::extractor::AuthUser;

    fn member(id: Uuid) -> AuthUser {
        AuthUser { id, email: "test@test.com".into(), role: "member".into(), organization_id: None }
    }

    fn admin(id: Uuid) -> AuthUser {
        AuthUser { id, email: "admin@test.com".into(), role: "admin".into(), organization_id: None }
    }

    #[test]
    fn member_can_edit_own_profile() {
        let user_id = Uuid::new_v4();
        let user = member(user_id);
        assert!(can_edit_profile(&user, user_id, false));
    }

    #[test]
    fn member_cannot_edit_other_profile() {
        let user = member(Uuid::new_v4());
        let other_id = Uuid::new_v4();
        assert!(!can_edit_profile(&user, other_id, false));
    }

    #[test]
    fn admin_can_edit_non_owner_profile() {
        let user = admin(Uuid::new_v4());
        let other_id = Uuid::new_v4();
        assert!(can_edit_profile(&user, other_id, false));
    }

    #[test]
    fn admin_cannot_edit_org_owner_profile() {
        let user = admin(Uuid::new_v4());
        let owner_id = Uuid::new_v4();
        assert!(!can_edit_profile(&user, owner_id, true)); // is_org_owner = true
    }
}
```

Run them:
```bash
cargo test --lib  # runs all unit tests, no database needed
```

These run in milliseconds. No network, no database, no setup. This is the value of pure functions — they're inherently testable.

## RBAC: Permission Middleware — `src/middleware/rbac.rs`

RBAC in Rust is a function that takes the current user and a required permission, queries the database, and returns an error if the user doesn't have it.

```rust
use axum::{
    extract::State,
    http::StatusCode,
    Json,
};

use crate::{auth::extractor::AuthUser, errors::AppError, state::AppState};

/// Check if the user has a specific permission via the database.
pub async fn check_permission(
    user: &AuthUser,
    permission: &str,
    state: &AppState,
) -> Result<(), AppError> {
    let has_permission = sqlx::query!(
        r#"
        SELECT 1 as exists
        FROM role_permissions rp
        JOIN permissions p ON rp.permission_id = p.id
        JOIN roles r ON rp.role_id = r.id
        WHERE r.name = $1
          AND p.name = $2
        "#,
        user.role,
        permission
    )
    .fetch_optional(&state.db)
    .await
    .map_err(AppError::Internal)?;

    if has_permission.is_none() {
        return Err(AppError::Forbidden);
    }

    Ok(())
}

/// Convenience function for requiring a specific role (no DB query needed).
pub fn require_role(user: &AuthUser, role: &str) -> Result<(), AppError> {
    if user.role != role {
        return Err(AppError::Forbidden);
    }
    Ok(())
}
```

### Using RBAC in Handlers

```rust
pub async fn create_product(
    auth: AuthUser,
    State(state): State<AppState>,
    Json(body): Json<CreateProductRequest>,
) -> Result<Json<ProductResponse>, AppError> {
    // RBAC: only users with products:write permission
    check_permission(&auth, "products:write", &state).await?;

    // Proceed with creation
    // ...
}

pub async fn list_all_subscriptions(
    auth: AuthUser,
    State(state): State<AppState>,
) -> Result<Json<Vec<Subscription>>, AppError> {
    // RBAC: simple role check — no DB query needed
    require_role(&auth, "admin")?;

    // Proceed
    // ...
}
```

The `?` operator makes this clean: if `check_permission` returns `Err(AppError::Forbidden)`, it propagates immediately. The rest of the handler doesn't execute.

## Using Both RBAC and ABAC Together

From Lesson 3.3, you know the pattern: RBAC first (role gate), then ABAC (context check).

```rust
pub async fn cancel_subscription(
    auth: AuthUser,
    Path(subscription_id): Path<Uuid>,
    State(state): State<AppState>,
) -> Result<Json<serde_json::Value>, AppError> {
    // 1. RBAC: must have permission to manage subscriptions
    check_permission(&auth, "subscriptions:manage", &state).await?;

    // 2. Fetch the subscription
    let subscription = sqlx::query_as!(
        Subscription,
        "SELECT * FROM subscriptions WHERE id = $1",
        subscription_id
    )
    .fetch_optional(&state.db)
    .await
    .map_err(AppError::Internal)?
    .ok_or(AppError::NotFound)?;

    // 3. ABAC: can this specific user cancel this specific subscription?
    if !can_cancel_subscription(&auth, subscription.user_id) {
        return Err(AppError::Forbidden);
    }

    // 4. Business logic: subscription already canceled?
    if subscription.is_canceled() {
        return Err(AppError::bad_request(
            "ALREADY_CANCELED",
            "This subscription is already canceled.",
        ));
    }

    // 5. Proceed with cancellation
    // ...
}
```

Three checks, each doing a different job:
- RBAC → does this role have the permission at all?
- ABAC → does this user own this subscription?
- Business rule → is the action valid in the current state?

## Why Not Use Axum Middleware for RBAC?

Axum has a middleware system (`tower::ServiceBuilder`, `axum::middleware::from_fn`). You could write RBAC as tower middleware. Here's why we don't:

**The problem:** HTTP middleware runs before the handler, but RBAC usually depends on what the handler is doing — and sometimes on data the handler needs to fetch (like what subscription belongs to what user).

In Node.js, the pattern `router.get('/subscriptions/:id', authenticate, requirePermission('subscriptions:manage'), handler)` chains middleware in order. It works for simple permission checks. But when you need to check "is this user the owner of subscription X?", you need to fetch subscription X first — which the handler does. There's no clean way to express that in middleware.

**The Axum approach:** Auth lives in the extractor (`AuthUser`), permission and policy checks live in the handler body. The extractor guarantees the user is authenticated; the handler decides what level of authorization is required for the specific operation.

This is more explicit, more flexible, and easier to test.

## The Hospital Example Revisited

From Lesson 0.3, the hospital system that uses both RBAC and ABAC:

```rust
// RBAC: must be a doctor to access medical records
fn require_doctor(user: &AuthUser) -> Result<(), AppError> {
    if user.role != "doctor" {
        return Err(AppError::Forbidden);
    }
    Ok(())
}

// ABAC: doctor can only view patients assigned to them in their department
fn can_view_patient_record(
    doctor: &AuthUser,
    patient_doctor_id: Uuid,
    patient_dept_id: Uuid,
    doctor_dept_id: Uuid,
) -> bool {
    let is_assigned = doctor.id == patient_doctor_id;
    let same_department = patient_dept_id == doctor_dept_id;
    is_assigned && same_department
}

// Handler
async fn view_patient_record(
    auth: AuthUser,
    Path(patient_id): Path<Uuid>,
    State(state): State<AppState>,
) -> Result<Json<PatientRecord>, AppError> {
    // RBAC: must be a doctor
    require_doctor(&auth)?;

    // Fetch patient data
    let patient = fetch_patient(&state.db, patient_id).await?;

    // ABAC: must be assigned to this patient AND in the same department
    if !can_view_patient_record(&auth, patient.doctor_id, patient.department_id, auth.department_id) {
        return Err(AppError::Forbidden);
    }

    Ok(Json(patient.into_record()))
}
```

The structure is always the same: RBAC gate → fetch data → ABAC check → proceed.
