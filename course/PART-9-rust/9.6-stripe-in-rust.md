# Lesson 9.6 — Stripe Integration in Rust

## The Two Parts

Stripe integration in this project has two sides:

1. **Outbound calls** — your server calls Stripe's API to create customers, products, prices, subscriptions (`src/services/stripe.rs`)
2. **Inbound webhook** — Stripe calls your server when events happen (`src/routes/webhooks.rs`)

The outbound side is straightforward: HTTP client (reqwest) calling Stripe's REST API. The inbound side is where precision matters most: signature verification, idempotency, and response ordering.

---

## Outbound: The Stripe Client — `src/services/stripe.rs`

```rust
use reqwest::Client;
use serde_json::Value;

pub struct StripeClient {
    client: Client,
    secret_key: String,
    base_url: String,
}

impl StripeClient {
    pub fn new(config: &Config) -> Self {
        Self {
            client: Client::new(),
            secret_key: config.stripe_secret_key.clone(),
            base_url: "https://api.stripe.com/v1".to_string(),
        }
    }

    async fn post(&self, path: &str, params: &[(&str, &str)]) -> Result<Value, AppError> {
        let response = self
            .client
            .post(format!("{}{}", self.base_url, path))
            .basic_auth(&self.secret_key, None::<&str>)
            .form(params)
            .send()
            .await
            .map_err(|e| anyhow::anyhow!("Stripe request failed: {}", e))
            .map_err(AppError::Internal)?;

        let status = response.status();
        let body: Value = response
            .json()
            .await
            .map_err(|e| anyhow::anyhow!("Failed to parse Stripe response: {}", e))
            .map_err(AppError::Internal)?;

        if !status.is_success() {
            let error_msg = body["error"]["message"]
                .as_str()
                .unwrap_or("Unknown Stripe error");
            return Err(AppError::bad_request("STRIPE_ERROR", error_msg));
        }

        Ok(body)
    }
}
```

**Why `.form(params)` instead of JSON?**

Stripe's API uses `application/x-www-form-urlencoded` for most endpoints (the same format as HTML form submissions). The `params` parameter is a slice of key-value string pairs:

```rust
// This encodes as: email=user%40example.com&metadata[user_id]=abc123
&[
    ("email", email),
    ("metadata[user_id]", user_id),
]
```

Nested objects use bracket notation: `metadata[user_id]`. Stripe's form encoding is documented in their API reference.

**Authentication:**

Stripe uses HTTP Basic Auth with the secret key as the username and an empty password:
```
Authorization: Basic base64(secret_key:)
```

The `basic_auth(&self.secret_key, None::<&str>)` call does this automatically.

## Creating a Customer

```rust
pub async fn create_customer(&self, email: &str, user_id: &str) -> Result<Value, AppError> {
    self.post(
        "/customers",
        &[
            ("email", email),
            ("metadata[user_id]", user_id),
        ],
    )
    .await
}
```

Called during registration:

```rust
// In routes/auth.rs register handler
let customer = state.stripe.create_customer(&body.email, &user_id.to_string()).await?;
let stripe_customer_id = customer["id"].as_str().unwrap_or("").to_string();

sqlx::query!(
    "INSERT INTO users (id, email, ..., stripe_customer_id) VALUES ($1, $2, ..., $3)",
    user_id, body.email, ..., stripe_customer_id
)
.execute(&state.db)
.await?;
```

The `metadata[user_id]` allows you to find your user from a Stripe customer object later. When Stripe sends you a webhook with a customer object, you can look up the user in your database using this metadata.

## Creating Subscriptions

For subscriptions, you need the Stripe customer ID, the Stripe price ID, and optionally a trial period:

```rust
pub async fn create_subscription(
    &self,
    customer_id: &str,
    price_id: &str,
    trial_period_days: Option<i64>,
) -> Result<Value, AppError> {
    let trial_days_str;
    let mut params = vec![
        ("customer", customer_id),
        ("items[0][price]", price_id),
    ];

    if let Some(days) = trial_period_days {
        trial_days_str = days.to_string();
        params.push(("trial_period_days", &trial_days_str));
    }

    self.post("/subscriptions", &params).await
}
```

The `items[0][price]` notation is Stripe's way of encoding an array in form data. Stripe subscriptions support multiple line items; using `[0]` specifies the first (and in this case only) item.

## Inbound: Webhook Handler — `src/routes/webhooks.rs`

### Step 1: Receive the Raw Body

This is the most common mistake in webhook implementations. Stripe verifies its signature against the **raw bytes** of the request body. If you let any middleware parse or transform the body first, the signature check fails.

In Axum, you use `axum::body::Bytes` to receive the raw body:

```rust
pub async fn stripe_webhook(
    State(state): State<AppState>,
    headers: HeaderMap,
    body: Bytes,             // ← raw bytes, not parsed
) -> Result<Json<Value>, (StatusCode, Json<Value>)> {
```

If you used `Json<Value>` here instead, Axum would parse the JSON before your handler runs, and the raw bytes would be gone. The signature verification would have nothing to verify against.

### Step 2: Verify the Signature

Stripe signs every webhook request using HMAC-SHA256. The algorithm:

```
Stripe-Signature: t=1714000000,v1=abc123...
```

Verification steps:
1. Extract `t` (timestamp) and `v1` (signatures) from the header
2. Build the signed payload: `"timestamp.rawBody"`
3. Compute HMAC-SHA256 of the signed payload using your webhook secret
4. Compare to the `v1` signatures

```rust
fn verify_stripe_signature(
    payload: &[u8],
    signature_header: &str,
    secret: &str,
) -> Result<(), AppError> {
    let mut timestamp = None;
    let mut signatures: Vec<&str> = Vec::new();

    for part in signature_header.split(',') {
        if let Some(ts) = part.strip_prefix("t=") {
            timestamp = Some(ts);
        } else if let Some(sig) = part.strip_prefix("v1=") {
            signatures.push(sig);
        }
    }

    let timestamp = timestamp.ok_or_else(|| {
        AppError::bad_request("INVALID_SIGNATURE", "Missing timestamp in Stripe signature.")
    })?;

    let signed_payload = format!(
        "{}.{}",
        timestamp,
        std::str::from_utf8(payload).unwrap_or("")
    );

    let mut mac = HmacSha256::new_from_slice(secret.as_bytes())
        .map_err(|_| AppError::bad_request("SIGNATURE_ERROR", "Invalid webhook secret."))?;
    mac.update(signed_payload.as_bytes());
    let expected = hex::encode(mac.finalize().into_bytes());

    let verified = signatures
        .iter()
        .any(|sig| constant_time_eq::constant_time_eq(sig.as_bytes(), expected.as_bytes()));

    if !verified {
        return Err(AppError::bad_request(
            "INVALID_SIGNATURE",
            "Webhook signature verification failed.",
        ));
    }

    Ok(())
}
```

**Why `constant_time_eq` instead of `==`?**

String comparison with `==` short-circuits: it returns false as soon as it finds the first differing character. This means if an attacker makes thousands of requests with slightly different signatures, they can measure response times to learn byte-by-byte what the correct signature is. Constant-time comparison always takes the same amount of time regardless of where the strings differ.

Stripe provides multiple `v1` signatures in the header (during key rotation). The `any()` check accepts the event if any of them match.

### Step 3: Return 200 Immediately, Process Asynchronously

This is critical. From Lesson 5.5:

> "If your handler takes too long (>30 seconds), Stripe marks the webhook as failed and retries."

```rust
// Respond to Stripe immediately
let state_clone = state.clone();
let event_clone = event.clone();

tokio::spawn(async move {
    if let Err(e) = process_event(state_clone, event_id, event_type, event_clone).await {
        tracing::error!("Webhook processing error: {:?}", e);
    }
});

// This returns immediately — before process_event completes
Ok(Json(json!({ "received": true })))
```

`tokio::spawn` launches the processing in the background. The HTTP response goes back to Stripe in milliseconds. The actual database work happens in parallel.

In production, you'd push the event to a queue (Redis, SQS, etc.) instead of spawning directly. For this project, spawning is sufficient.

### Step 4: Check Idempotency

Stripe will retry webhooks if your server doesn't respond with 2xx in time. This means you must handle the same event arriving multiple times.

```rust
async fn process_event(
    state: AppState,
    event_id: String,
    event_type: String,
    payload: Value,
) -> Result<(), anyhow::Error> {
    // Fast path: already processed?
    let existing = sqlx::query!(
        "SELECT id, processed_at FROM webhook_events WHERE stripe_event_id = $1",
        event_id
    )
    .fetch_optional(&state.db)
    .await?;

    if let Some(e) = &existing {
        if e.processed_at.is_some() {
            tracing::info!("Webhook {} already processed, skipping", event_id);
            return Ok(()); // ← exit early, no duplicate processing
        }
    }

    // Insert record if it doesn't exist
    if existing.is_none() {
        sqlx::query!(
            r#"
            INSERT INTO webhook_events (id, stripe_event_id, event_type, payload)
            VALUES (uuid_generate_v4(), $1, $2, $3)
            ON CONFLICT (stripe_event_id) DO NOTHING
            "#,
            event_id,
            event_type,
            payload
        )
        .execute(&state.db)
        .await?;
    }

    // Process the event
    let result = match event_type.as_str() {
        "customer.subscription.updated" => {
            on_subscription_updated(&state, &payload["data"]["object"]).await
        }
        "customer.subscription.deleted" => {
            on_subscription_deleted(&state, &payload["data"]["object"]).await
        }
        "invoice.paid" => on_invoice_paid(&state, &payload["data"]["object"]).await,
        "invoice.payment_failed" => {
            on_invoice_payment_failed(&state, &payload["data"]["object"]).await
        }
        _ => {
            tracing::debug!("Unhandled webhook event type: {}", event_type);
            Ok(())
        }
    };

    // Mark as processed (or record error)
    match result {
        Ok(()) => {
            sqlx::query!(
                "UPDATE webhook_events SET processed_at = NOW() WHERE stripe_event_id = $1",
                event_id
            )
            .execute(&state.db)
            .await?;
        }
        Err(e) => {
            sqlx::query!(
                "UPDATE webhook_events SET error = $1 WHERE stripe_event_id = $2",
                e.to_string(),
                event_id
            )
            .execute(&state.db)
            .await?;
            return Err(e);
        }
    }

    Ok(())
}
```

**The idempotency guarantee has two layers:**

1. **Code check:** `if e.processed_at.is_some() { return Ok(()); }` — if we've seen and processed this event, skip it
2. **Database constraint:** `ON CONFLICT (stripe_event_id) DO NOTHING` on the `webhook_events` table — if two concurrent requests for the same event arrive simultaneously, only one INSERT succeeds; the other is silently ignored

The UNIQUE constraint on `stripe_event_id` is defined in the migration:
```sql
UNIQUE(stripe_event_id)
```

## Event Handlers

Each event type maps to a handler that updates your database state:

```rust
async fn on_subscription_updated(
    state: &AppState,
    subscription: &Value,
) -> Result<(), anyhow::Error> {
    let stripe_sub_id = subscription["id"].as_str().unwrap_or("");
    let status = subscription["status"].as_str().unwrap_or("");
    let cancel_at_period_end = subscription["cancel_at_period_end"].as_bool().unwrap_or(false);

    sqlx::query!(
        r#"
        UPDATE subscriptions
        SET status = $1, cancel_at_period_end = $2, updated_at = NOW()
        WHERE stripe_subscription_id = $3
        "#,
        status,
        cancel_at_period_end,
        stripe_sub_id
    )
    .execute(&state.db)
    .await?;

    Ok(())
}
```

The pattern is identical across all handlers:
1. Extract the relevant fields from the Stripe event payload
2. Update your database
3. Return `Ok(())`

If the database update fails, the error is recorded in `webhook_events.error` and the event stays unprocessed. Stripe will retry, giving you another chance.

## Testing Webhooks Locally

```bash
# Install Stripe CLI
brew install stripe/stripe-cli/stripe

# Log in
stripe login

# Forward events to your local server
stripe listen --forward-to localhost:3000/api/v1/webhooks/stripe

# This prints your webhook signing secret:
# > Ready! Your webhook signing secret is whsec_test_...
# Add this to your .env as STRIPE_WEBHOOK_SECRET

# Trigger a specific event
stripe trigger customer.subscription.updated
stripe trigger invoice.paid
stripe trigger customer.subscription.deleted
```

The Stripe CLI generates real webhook payloads with real signatures. Your `verify_stripe_signature` function will correctly verify them. This is the correct way to test — not by mocking.

## What the Node.js Version Does the Same Way

- Raw body parsing (Express needs `express.raw()` middleware; Axum uses `Bytes`)
- HMAC-SHA256 signature verification (same algorithm, different library)
- Idempotency: same UNIQUE constraint, same code check
- Async processing: `setImmediate` or background job in Node.js, `tokio::spawn` in Rust
- Event routing: `switch` in Node.js, `match` in Rust — identical logic

The mental model from Lesson 5.5 carries over exactly. Only the syntax changes.
